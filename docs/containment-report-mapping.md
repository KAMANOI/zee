# 封じ込め証跡エクスポートと報告義務 — 一次資料調査と項目対応表

`zee export`（CLI）/ `query_containment_report`（MCP、read-only）が実装する内容の根拠文書。実装は本ファイルの対応表と同期させること（ズレたらどちらかが古い）。

## この文書の確度についての注記（必読）

この調査は Web 検索・WebFetch による一次資料相当の資料への到達を試みたが、**e-Gov 法令検索の条文本文そのものには到達できていない**（JS レンダリングのためツールで空を返し、フォールバックの `curl`/API 取得も本タスクでは行っていない）。根拠として使ったのは：

- 衆議院の法案ページ（`shugiin.go.jp`、一次資料＝国会提出法案そのもの）
- 内閣府サイバー安全保障の公表資料（`cao.go.jp`、政府一次資料）
- worldjpn.net（大学系の政策文書データベース。**法令の非公式ミラー**であり e-Gov そのものではない — 条文の逐語性は未照合）
- JPCERT/CC 公式サイトの報告様式（一次資料。実物を確認）
- 法律事務所・コンサルティングファームの解説記事（**二次資料**。参考程度）

したがって以下の表で「確認済み」としている項目のうち、**条文番号までの厳密な裏取りが取れているのは衆議院法案ページ・内閣府資料に基づく項目のみ**で、worldjpn.net 経由の項目は「確認済み（非公式ミラー、e-Gov未照合）」と読み替えること。主務省令・施行規則（報告様式の詳細）は本稿執筆時点（2026-10-01）で未公布のため、報告項目の細部は制度的に未確定である。

## 2. 民間事業者への報告義務

| 項目 | 対象事業者区分 | 法的性質 | 根拠 | 確度 |
|---|---|---|---|---|
| 特定重要電子計算機の導入届出 | 特定社会基盤事業者（基幹インフラのうち指定を受けた事業者のみ。基幹インフラ事業者全体ではない） | 法定義務 | 法第4条第1項相当 | 確認済み（非公式ミラー、e-Gov未照合） |
| 特定侵害事象の報告 | 同上 | 法定義務 | 法第5条相当 | 確認済み（非公式ミラー、e-Gov未照合） |
| 報告先 | 同上 | — | 事業所管大臣・内閣総理大臣（複数窓口の可能性） | 確認済み（非公式ミラー） |
| 報告期限（速報） | 同上 | 法定 | 認知から3〜5日以内 | 解釈（パブコメ・解説記事に基づく推定。省令未公布） |
| 報告期限（詳報） | 同上 | 法定 | 認知から30日以内 | 確認済み（非公式ミラー） |
| **個人への報告義務** | 個人 | **対象外（報告不要）** | — | 確認済み |
| **中小事業者への報告義務** | 中小事業者（特定社会基盤事業者に指定されない限り） | **対象外（報告不要）** | — | 確認済み |
| 警察への相談・届出 | 全事業者・個人 | **任意**（相談・支援名目、義務ではない） | 警察サイバー犯罪相談窓口 | 確認済み |
| JPCERT/CCへの報告 | 全事業者・個人 | **任意** | JPCERT/CC Webフォーム | 確認済み（実物確認） |

**Zeeの想定利用者（個人・中小事業者）への含意**：Zeeの標準的な利用者は法定報告義務の対象外である可能性が高い。法定義務がかかるのは「特定重要電子計算機を使用する特定社会基盤事業者」という指定を受けた限られた事業者のみで、Zeeがそれを自動判定する手段はない（利用者が自分で確認する前提。README にその旨明記）。

## 3. 無害化措置の実施主体（Zeeが行わない理由の根拠）

| 実施主体 | 根拠 | 実施条件 |
|---|---|---|
| 警察 | 警察官職務執行法改正 | 手続的適正確保・サイバー通信情報監理委員会の事前関与 |
| 自衛隊 | 自衛隊法改正 | ①重要電子計算機機能停止で国家・国民の安全を著しく損なうおそれ②自衛隊固有技術が不可欠③警察庁・国家公安委員会の要請/同意 |

民間・OSSツールに無害化の権限は無い。Zeeはこの表の実施主体になり得ないため、攻撃元へのアクセス・接続・停止機能を一切持たない（設計にも含めない）。

## 4. JPCERT/CC報告様式のフィールド（実物確認済み・任意提出用の参考様式）

**連絡先セクション**：お名前／組織名称／部署名／電話番号／電子メール
**報告目的**：情報提供／相談／関係サイトへの連絡希望 等
**インシデント情報セクション**：アクセス元IPアドレス・ホスト名／インシデント内容・状況の説明（自由記述）／発生したシステムのIPアドレス又はホスト名／プロトコル又はポート／関連ソフトウェア・ハードウェア／OS／発生時刻／タイムゾーン／ログ情報

## 5. 報道と一次資料の食い違い

| 報道表現 | より正確な表現 |
|---|---|
| 「基幹インフラ事業者に報告義務」 | 「特定社会基盤事業者のうち特定重要電子計算機を使用するもの」に限定 |
| 「30日以内に報告」 | 速報（3〜5日、解釈）と詳報（30日、確認済み）の二段階 |
| 俗称「能動的サイバー防御法」が先行 | 正式名称は「重要電子計算機に対する不正な行為による被害の防止に関する法律」 |

## 6. Zeeの記録項目 ↔ 報告項目 対応表（Phase 2）

`src/zee/telemetry/report_export.py` の `report_fields` を実装している対応関係。**推定値では埋めず**、Zeeが実際に記録していない項目は「不明（Zeeはこの情報を記録しません）」、報告者本人しか分からない項目は「利用者が記入」とする。

| 報告項目（JPCERT/CC様式ベース） | Zeeのデータ源 | 扱い |
|---|---|---|
| お名前・組織名称・部署名・電話番号・電子メール | なし | 利用者が記入 |
| 報告目的 | なし | 利用者が記入 |
| アクセス元IPアドレス・ホスト名 | なし（Zeeはファイルレベルの監視のみで、送信元IPを記録しない） | 不明（Zeeは記録しない） |
| インシデント内容・状況の説明（自由記述） | `events[].detail` + `source`/`op_class`/`confidence` から自動生成した要約文 | Zeeが自動生成（`incident_summary_auto`）。運用者の言葉での説明は別途 `incident_summary_operator` に利用者が記入 |
| 発生したシステムのIP/ホスト名 | `asset_id`（assets.toml で運用者が付けた識別子。IPアドレスではない） | Zeeが提供（`affected_asset_ids`）。IPではない点を明示 |
| プロトコル又はポート | なし（ファイル監視であり通信層を観測しない） | 不明（Zeeは記録しない） |
| 関連ソフトウェア・ハードウェア | なし | 利用者が記入 |
| 発生時刻 | `TrapEvent.detected_at`（実測記録） | Zeeが提供（`detected_at_first`/`detected_at_last`） |
| タイムゾーン | 常にUTC（`events.jsonl`のdetected_atはISO8601・UTC） | Zeeが提供（固定値） |
| ログ情報 | `events.jsonl`該当行（ハッシュチェーン付き） | Zeeが提供（`events`フィールドそのもの） |
| （法定・速報/詳報用）特定侵害事象の認知日時 | `detected_at_first` と同一データ | Zeeが提供。ただし「特定侵害事象」に該当するかの法的評価は利用者が行う |
| （法定）事業者名・連絡先 | なし | 利用者が記入 |
| （法定）省令様式の詳細項目 | — | 不明・現時点で対応不可（主務省令未公布のため） |

## 7. 改ざん検知の設計（Phase 2）

- **ハッシュチェーン**：`events.jsonl`/`metrics.jsonl` の各レコードに書き込み時点で `prev_hash`（直前レコードの `record_hash`、先頭は `GENESIS_HASH`）と `record_hash`（`sha256(prev_hash + 正規化JSON)`）を付与する（`telemetry/events_log.py` の `_append`/`verify_chain`）。ログローテーション（10MB超で `path.rename`）をまたいでもチェーンは継続する（ローテーション前にハッシュを読み取ってからリネームする順序で担保）。
- **検知できること**：1行の内容書き換え（`corrupted`）、1行の削除・並び替え（次の行が `chain_break`）。
- **検知できないこと（正直な限界）**：ファイル全体の差し替え・全行の一括改ざん（チェーンの起点から再計算されれば内部的には整合してしまう）。これに対しては `zee export` が出力するJSON/TXTとは**別の経路**で `export_sha256` を控える運用（提出メール本文への記載など）で補う。ファイル自体に埋め込んだダイジェストは、そのファイルが丸ごと差し替えられた場合には無意味である。
- **署名（採否）**：不採用。リポジトリに既存の非対称鍵基盤（ECDSA/P-256等）は存在しない（`grep -r "ECDSA\|P-256\|ecdsa" src/` で確認、ヒットなし）。`recovery/auth.py` は「Standard library only」の方針を明記しており、署名のために `cryptography` 等の新規依存を追加することは同方針と矛盾する。ハッシュチェーン＋別経路ダイジェストで「同一ホスト上の後からの改ざん検知」は満たせるため、非対称署名（真正性の非否認性）は本フェーズでは見送り、必要になれば別途の鍵基盤の設計判断として代表に上げる。
- **マスキング**：`--redact`（既定 on、MCPの `redact_paths` 既定と統一）は `detail`（自由記述、パスを含みうる）のみをマスクする。`asset_id` は運用者が assets.toml で付けた識別子であり、封じ込め範囲の特定に必要なためマスクしない（個人名を含む命名を避けるのは運用者の責任、と README に明記）。`decoy_ref` は元々絶対パスを含まない形式（`asset_id#index`）なのでマスク不要。
