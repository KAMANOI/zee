## 2. 表を読む前の前提：攻撃者がどこに立っていたかで答えが変わる

Zee の脅威モデルは**攻撃者がホスト（＝守る対象の端末・サーバーの中）にいる前提**で書かれている（`docs/containment-report-mapping.md` main:99「Zee の脅威モデルは攻撃者がホスト上にいる前提」）。本件についてお知らせが出しているのは「**影響の可能性のあるサーバー数： 26,739 件**」という数（お知らせ本文「1. 現時点で判明している内容」より。2026-10-25 取得）で、**実際に被害が出た件数も、同時に起きたかどうかも公表されていない（未確認）**。経路も公表されていない（F9）。したがって2つの場合があり、**どちらかは判断できない**。

| 場面 | 内容 | Zee の立ち位置 |
|---|---|---|
| **(a)** | 攻撃者が**各利用者のゲストOSの中**まで到達した（RDP・ゲスト内のプロセス実行など） | 下の3列表はこの場面を前提にしている |
| **(b)** | 攻撃者が**事業者の基盤側**（ハイパーバイザ・管理経路・仮想ディスク・スナップショット）から中身を読んだ | **ゲストOSの中の監視（watcher）は何も観測しない**（囮ファイルに触られず、ディスクの外側から読まれるため）。Zee に限らず、ゲスト内に入れるソフトでは原理的に見えない。**ただし「全行が効かない」とまでは言えない**：①囮の中身が持ち出され、埋め込まれた canary の URL を攻撃者が後から辿れば、利用者が指定した外部エンドポイントで発火する（`src/zee/decoy/canary_token.py` main:6-8＝URL を辿った時点で発火する作りで、辿る者がどこに立っているかは問わない。ただし `ZEE_CANARY_BASE_URL` を事前に設定していた場合のみ）。②それ以前に記録済みのローカルの記録と、外部通知（下の④参照）を事前に設定していた場合の送信済みの通知は、侵入経路に関係なく残る |

> **侵入経路は未公表。下の表は場面(a)を仮定した条件つきの評価であり、本件の経路を認定するものではない。経路が公表された時点でこの節と表を更新する。**

Zee の「入口」の定義も確認しておく：`docs/threat-model.md` main:10・139＝「Zee は入口を守らない」はネットワークの境界（FW・IDS/IPS）の話。`zee gate` は**自分が導入する物**（AIスキル・MCP・npm・PyPI・VS Code 拡張）を入れる前に調べる供給網の層であり、**攻撃者が勝手に置いたプログラムの検査には効かない**。

## 3. 3列対応表（場面(a)・ゲストOS＝Windows・Zee を利用者が入れていた場合）

| 事案の段階 | Zee が効くか（実装済みの機能・根拠の行） | Zee の層の外で必要な対策 |
|---|---|---|
| **① 不正なプログラムの設置**（F1・F2） | **×（置かれたこと自体は検知しない）**<br>Windows の watcher は **囮ファイルの親ディレクトリの変更通知だけ**を見る（`src/zee/watcher/backend_windows.py` main:3「Observes change notifications on the parent directories of decoys」）。`%TEMP%`・Program Files・スタートアップ等への設置は、Zee が見ている場所でなければ何も起きない。<br>**△（設置の後に囮を触れば検知）**：攻撃者が囮ファイルを**書き換え・削除・改名**した場合は change 系として検知し、通知する（`src/zee/responder/sequence.py` main:16-17）。<br>**×**：`zee gate` は導入前の持ち込み物の静的検査で、攻撃者が置いた物には使えない（`docs/threat-model.md` main:139）。マルウェアの削除・無効化・プロセス特定は行わない（`README.md` main:226「囮を触ったプロセスを報告しません」）。 | 事業者側の調査・駆除（F9）。サーバーの再構築（再開後に中身を信用して使い続けない）。EDR／AV など実行の監視を行う製品。OS とミドルウェアの更新。RDP の公開範囲の制限と多要素化。 |
| **② サーバー内の情報が閲覧された可能性**（F4） | **△ 条件つき・通知のみ。自動遮断はしない。**<br>・読み取り系の接触は **構造的に自動遮断しない**（`src/zee/responder/sequence.py` main:184-186＝`op_class != "change"` なら `cut_skipped_reason` を立てて遮断に進まない／`README.md` main:242・290）。通知文は「正規ソフトの可能性。心当たりがなければ確認し、`zee cut <asset_id>` で手動遮断してください」（`README.md` main:248）。<br>・**Windows では「読まれたこと」自体を OS から取れない**（`backend_windows.py` main:4-6＝SACL＋Object Access 監査が必要で MVP の対象外）。<br>・代わりに `ZEE_CANARY_BASE_URL` を設定していた場合のみ、囮の中に埋め込んだ URL を**攻撃者が辿った瞬間に**、利用者が指定した外部エンドポイントで発火する（`README.md` main:291／`src/zee/decoy/canary_token.py` main:10-11＝トークンを作って記録するだけで待ち受けはしない）。つまり**閲覧そのものではなく、閲覧した後の URL 参照を検知する**。未設定なら URL は埋め込まれず、「読むだけ」の接触は観測されない。<br>・**影響の段階表記（情報／注意／警戒／重大）は watcher が観測した接触にだけ付く。** Windows は読み取りを watcher が観測しないため（`backend_windows.py` main:3-6）、**canary の発火には段階表記も Zee の通知も付かない**（発火先は利用者が指定した外部エンドポイントで、Zee 本体には戻らない＝`README.md` main:291）。気づく手段は利用者側のそのエンドポイントだけ。 | 「何が置いてあったか」の棚卸し（Zee は中身の一覧を持たない）。暗号化しての保管。重要データをそのサーバーに置かない運用。閲覧の事実認定は事業者の調査（F5・F9）。 |
| **③ 認証情報の持ち出し・他サービスでの悪用の可能性**（F8） | **△ 条件つき。**<br>・囮が認証情報系テンプレート（`credentials` / `env` / `ssh_key`）なら、通知の重大度が「認証情報・鍵」として上がる（`tier.py` main:24・29・47-48）。表示のみ。<br>・攻撃者が囮を**変更系**で触った場合に限り、`response_mode: auto` **かつ** `dry_run: false` **かつ** `cut_method: egress` を明示していれば外向き通信の遮断が走る。**`cut_method` を省略すると既定は `full`** で、こちらは外向きだけでなく**ネットワークそのものを落とす**（Windows ではインターフェースを無効化する）ため、遠隔操作しているサーバーでは自分も入れなくなる。下に書く「既存の接続は通る」は `egress` の話で、`full` には当てはまらない（`sequence.py` main:16-17／**既定は `dry_run: true`**＝`src/zee/config/schema.py` main:43／`README.md` main:123）。<br>・Windows の遮断経路は `netsh advfirewall`（`src/zee/responder/cut_egress.py` main:508）。**条件として正直に書くべき4点**：(i) v0.12.0 以前は Windows の遮断が機能していなかった（v0.13.0 で修正・`README.md` main:125）、(ii) 検証は GitHub の英語版 Windows 仮想ランナーのみで**実機なし・日本語版での実測なし**（`README.md` main:211「Windows 実機未検証」・main:222・`docs/verification/real-cut.md` main:56）、(iii) **IPv4 のみ実測、IPv6 は未確認**（`README.md` main:127／`real-cut.md` main:50）、(iv) **遮断前から開いていた接続は止まらない**（新規接続のみ・`real-cut.md` main:30）。<br>**×（この段階に使えない機能）**：<br>・**持ち出し承認（egress approval）は使えない。** 実体は macOS の pf 規則を**テキストで生成するだけ**の試作で、ネットワークには触らない（`src/zee/egress/pf.py` main:1-4「Render (never run)」「Prototype limit: this only produces text」）。Windows 用の実施部分は無く、**CLI にも入口が無い**（`src/zee/cli.py` main のサブコマンドは init / watch / restore / init-restore-token / cut / doctor / status / export / incident-report / capability / mcp / gate / dilute のみ）。<br>・**権限分離（privsep）も使えない。** root デーモン＋Unix ソケット＋LaunchDaemon/systemd 前提（`src/zee/privsep/daemon.py` main:3-4）で Windows 向けではない。 | **お知らせの依頼事項の実行（Zee では代替できない）**：サーバー内に置いた ID・パスワードの変更、同一パスワードを使っている他サービスの変更（F8）。多要素認証の有効化。FX 口座・証券口座側の履歴確認と出金先の確認。API キー・EA の設定ファイルの再発行。パスワード管理ソフトへの移行（サーバー内に平文で置かない）。 |

### 補足：価値を下げる層（`src/zee/dilution/`）
ダミーの個人情報を混ぜて盗んだデータの価値を下げる生成器が入っている（`src/zee/dilution/generate.py` ほか）。**ファイルを出力するだけで、どこに置くかは利用者が決める**。生成の機能があることは確認済みだが、**「読まれても使えるデータが減る」という効果自体は未確認の仮説**である（実データを減らすわけではなく、混ぜる作業は利用者が行う。効果は混入の仕方・同時に流出したか・見分けのつきにくさに依存する）。閲覧そのものを止めも検知もしない。今回の事案では**事前に置いていなければ何も起きない**。

## 4. 要点（この表が言っていること）

1. **②「閲覧された可能性」が本件の中心だが、そこは Zee が自動で止める層ではない。** 読み取り系は設計として自動遮断せず通知のみ（`sequence.py` main:184-186）。Windows では読み取りを OS から取れないため、`ZEE_CANARY_BASE_URL` を事前に設定していた場合に限り「攻撃者が囮に埋め込まれた URL を辿った」という形で、**利用者が用意した外部エンドポイント側で**気づける（Zee の通知には出ない）。
2. **Zee が自動で止められるのは「囮を変更系で触られた時の通信」だけ**で、`response_mode: auto` ＋ `dry_run: false`（既定は dry_run）＋ **`cut_method: egress`** を明示していることが条件。**`cut_method` を省略すると既定は `full`** で、外向きだけでなくネットワークそのものを落とす（Windows ではインターフェースを無効化する）ため、遠隔で使っているサーバーでは自分も入れなくなる。`egress` の場合、Windows は実機未検証・IPv4 のみ実測で、**既に確立している接続は止まらない**（この「止まらない」は `egress` に限った話で、`full` には当てはまらない）。
3. **①の不正プログラムの設置と④の事業者側の停止は Zee の層の外。** ③の認証情報の変更は Zee では代替できず、お知らせの依頼事項をそのまま実行する必要がある。
4. **経路が基盤側だった場合（場面(b)）に効かなくなるのは「ゲストOSの中の監視（watcher）が観測する行」だけ。** 囮に埋め込んだ URL を攻撃者が後から辿れば canary は発火しうるし、それ以前に残った記録と、事前に設定していた外部通知は残る（§2(b)・④参照）。続報で経路が公表されたら §2 と表を更新する。
