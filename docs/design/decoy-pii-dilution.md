# ダミー個人情報レコード生成 — 設計書（非公開メモ・push禁止）

> **この文書・このブランチは代表の採否判断が出るまで `git push` しないこと。**
> 既存の Zee README・LP の「過剰主張をしない」方針をこの文書にも適用する：
> 効果を断定する表現（「見分けられません」「防げます」）を使わず、
> 「確認済み」と「推測」を常に分けて書く。

## 0. 目的（指示書より）

流出しうるデータに、実在の人と決して重ならないダミーの個人レコードを混ぜ、
盗まれたデータ1件あたりの売値を下げる。検知は別件（既存の `src/zee/decoy/`
canary トークン・`src/zee/gate/sandbox/decoys.py` はファイルシステムの侵入検知用で、
本件（DBレコードの価値毀損）とは目的もコードも重ならない。再利用なし、新規実装）。

## 1. 一次資料の確認結果（確認済み／推測を明示）

着手前に4つの候補データソースを一次資料で確認した（doc-fetcher agent 4件、2026-10-09実施）。

| データソース | 粒度 | 非居住判定に使えるか | ライセンス | 備考 |

| **アドレス・ベース・レジストリ**（デジタル庁） | **確認済み**：町字マスター（町名の文字一覧・ジオメトリなし）のみ公開済み | 地番・住居表示マスターは**2026年度から開発着手予定（未公開・仕様未決定）** | **確認済み**：PDL1.0、商用・再配布可（出典明記） | 「存在する町名の完全な一覧」として使える＝Layer 1（架空町名）の非実在確認に使う |

### 結論：非居住番地の判定方法は確定できる（条件付き）

単独で十分なデータソースは無かったが、**2つの確認済み一次資料の組み合わせ**で成立する。

1. **登記所備付地図データ**から、対象市区町村の地番ポリゴン（**必ず「公共座標系」版を使う**。
   「任意座標系」版は地理的に位置合わせされておらず本件には使えない。全1.7億筆のうち
   公共座標系は1.1億筆＝さらにカバレッジが絞られる、という点も一次資料の数字から導かれる
   **推測**であり実際の按分は未確認）。
2. **国土数値情報 都市公園(P13)・河川区域**ポリゴンと空間結合し、
   地番ポリゴンの全頂点が公園・河川区域ポリゴンの内側にある地番だけを「非居住番地」とする
   （一部だけ重なる境界地番は除外＝安全側に倒す。駐車場は指示書の推奨どおり対象外＝
   用途変更が頻繁で「確実に非居住」と言えないため採用しない）。
3. 地番（例：「○○一丁目45番」）に含まれる町名を**アドレス・ベース・レジストリの町字マスター**
   と突き合わせ、実在する町名であることを確認する（地番データの町名表記ゆれの検出にも使う）。

この手順で得られる地番は「公園・河川として法的に指定された土地の中にある地番」であり、
建物が建てば用途地域・占用許可の点で通常の宅地と性質が異なる。**「将来にわたって絶対に
住居表示が付かない」という法的保証ではない**（指示書補足2が求める「確実な判定」は、
統計的・制度的な強い裏付けであって数学的証明ではない、という前提で進める。この前提が
代表の意図と異なる場合は不採用とすべき、という点を代表確認事項に挙げる）。
再抽出のたびに公園・河川の指定が変わっていないか確認する（§5）ことで、指定解除による
後追いのリスクを縮小する。

### 確認できなかった／保留にした点

- 地番データの入手は**G空間情報センターのUI操作が前提**で、プログラムからの自動取得経路は
  一次資料で確認できなかった。→ 本設計はこの前提で「利用者が定期的に手動ダウンロードし、
  CLIにファイルパスを渡す」方式にする（§4）。「生成のたびに自動再取得」はできない。
- 登記所備付地図データの地目・公有地フラグの有無は未確認。本設計は地目に依存せず
  空間結合のみで判定するため、影響なし。
- 都市公園・河川区域データの更新頻度は不明。再抽出時に鮮度を記録し、古い抽出での生成を
  警告する（§5）。

## 2. 二層構成

### Layer 1：架空の町名

- 実在しない町名（例：「○○市架空台三丁目」のような、実在の命名規則に沿うが
  アドレス・ベース・レジストリの町字マスター（全国・確認済み）に存在しない文字列）を生成。
- 判定は単純な完全一致チェック（CSV突き合わせ、stdlibのみ）。マスターにある限り
  「存在しない」と言い切れる、最も確実な層。
- 番地・部屋番号は自由に付与してよい（実在しない町名の時点で実在住所と重複しない）。

**【代表回答 2026-10-13：「架空町名だけ」】** 公園・河川の土地を使う Layer 2 は「将来も絶対に住所にならない
保証がない」ため、採用しない。運用上の対象は Layer 1 のみ（CLI 既定も `fictional-town`）。
Layer 2 のコード・テストは削除せず残す（資産を減らさない）が、非推奨・実データ投入禁止。
`real-nonresidential` / `both` を使う場合は代表の再判断が要る。

### Layer 2：実在住所＋架空の建物名・部屋番号（非居住番地）

- §1で確定した「公園・河川区域に全体が含まれる地番」の町名＋地番を使う。
- その地番に、架空の建物名（例：「○○ハイツ」等、実在建物名と機械的に重複しないよう
  同一地番内の既存建物名簿は存在しないため単純に生成規則でよい）と架空の部屋番号を付与する。
- **代表指示の絶対条件**：この層は実在の人と絶対に重ならないこと。§1の判定を通った地番
  以外では生成しない。**fail-closedの正確な意味（独立レビューで文言と実装の不一致を
  指摘され訂正・2026-10-09）**：候補の地番群のうち判定を通らない物件は黙って除外する
  （市区町村内の大半の地番が住宅地＝判定落ちするのは正常であり、1件でも判定落ちしたら
  市区町村全体を使用不能にするという意味ではない）。fail-closedが発動するのは、
  除外した結果**適格な地番が1件も残らなかった場合のみ**で、その時はLayer 2のレコードを
  一切生成しない（Z801）。

## 3. 統計整合（氏名・年齢・性別・郵便番号）

- **氏名**：よく使われる姓・名を複数の頻度帯（多い/中位/少ない）に分けた自作の簡易リストを
  使う。**これは公式統計ではなく推測ベースの簡易モデル**であり、「実際の統計分布と一致する」
  とは主張しない（Zeeの過剰主張禁止方針を踏襲）。性別と名の対応も同リストで持つ。
- **年齢・性別**：年齢は0〜100の大まかな人口ピラミッド型の重み付け（推測モデル）、
  性別は二値をおよそ半々で割り当てる。
- **郵便番号**：日本郵便「郵便番号データ」（KEN_ALL.CSV）を使う。**確認済み**：日本郵便公式
  readme に「郵便番号データに限っては日本郵便株式会社は著作権を主張しません。自由に配布
  していただいて結構です」と明記（再配布・同梱に制約なし）。
  - Layer 2：実在町名に対応する実在郵便番号をそのまま使う（整合性が最も高い）。
  - Layer 1：架空町名が属すると称する実在市区町村の郵便番号のうち、代表的な1件
    （例：その市区町村の代表郵便番号）を使う。町名までは一致しないが、市区町村単位では
    一致する。これ以上の精緻化（架空町名専用の郵便番号帯を作る等）はしない＝実在の
    郵便番号帯を侵食するリスクがあるため。
- 電話番号・メールアドレスは統計整合の対象外（§6で別途扱う）。

## 4. 混入先・初版のスコープ

- 指示書の技術判断どおり、**初版はファイル出力まで**（ダミーレコード＋台帳をファイルに
  書き出し、本番DB・バックアップへの実際の混入は利用者が行う）。Zeeの利用者DBへの
  直接書き込みは「読み取り系は通知のみ・変更系の自動操作は封じ込めに限る」という
  既存の設計思想と性質が異なるため、範囲外とする。
- 出力形式はCSV（UTF-8）を既定とする。理由：本番DBへの直接INSERTよりも、エクスポート・
  バックアップへの追記（`COPY`/`LOAD DATA`等）に乗せやすく、本番の集計・業務ロジックを
  汚しにくい。
- **推奨（代表確認不要・設計判断）**：混入先は本番DBそのものではなく、バックアップ・
  ダンプ・外部エクスポートへの追記を既定の使い方として案内する。本番テーブルに直接
  混ぜると、社内の集計・検索・重複排除ロジックがダミーを実データとして扱ってしまう
  （売上集計のズレ、カスタマーサポートの誤表示等）。バックアップ・ダンプは「流出時に
  まとまって持ち出される複製」であり本来の目的（盗まれた時に薄める）に最も効く対象でもある。
  本番に混ぜたい場合は、アプリ側で台帳のIDを除外フィルタに登録する運用が前提になる
  （利用者の責任、Zeeはそこまで面倒を見ない＝v1はファイル出力のみ）。

## 5. 台帳（ledger）とダミーの見分け方

- ダミーのレコード自体には目印を一切持たせない（流出したデータから除去されないように
  するため、代表の要求どおり）。
- 台帳は生成時にのみ利用者の手元に残すファイル（`ledger.jsonl`、ダミーの出力ファイルとは
  別のファイル・別の置き場所を利用者に案内）。各行は
  `{"dummy_id": "<ランダムID>", "record_hmac": "<HMAC-SHA256>"}`。
  - `record_hmac` はレコードの正規化文字列（氏名・住所・生年月日等を固定順で連結）を、
    **利用者ごとの秘密シード（seed）を鍵としたHMAC-SHA256**で計算する。
  - 公開済みのZeeのソースコードだけでは、シードを知らない限りこのHMACを再計算できない
    ＝台帳が部分的に流出しても、コード単体・台帳単体では実データからダミーを逆引きできない。
  - 利用者は自分の実データ1件ごとに同じ正規化・同じシードでHMACを計算し、台帳と一致すれば
    ダミーと判定して業務から除外できる（具体的な正規化手順はCLIのヘルパーとして提供）。
- シードは利用者が`--seed`で指定するか、未指定ならCLIが`secrets.token_hex`で生成し
  **標準出力にのみ表示**（ファイルにもログにも残さない）。利用者が保管する前提。

## 6. 電話番号・メールアドレス（代表回答済み）

**【代表回答 2026-10-13：選択肢B「自分の宛先」】** メールは利用者が管理するドメインの
宛先にする（既定）。電話番号は下記の推奨どおり空欄のまま（自分管理の着信を用意する
コストが高いため。代表回答は「①B」でメール・電話の分け方は推奨案を採用した解釈）。
`--email-mode` の既定は `user-domain`（`--email-domain` 必須。未指定はZ802で停止＝
利用者ドメインが無いまま静かに空欄へ落ちない）。`omit` は明示指定した時だけ。
以下は検討経緯と弱点の記録として残す。

- **選択肢A：ダミーに含めない**（nullまたは空欄）。実在の人の電話・メールと重複するリスクが
  構造的にゼロ。一方、レコードの「厚み」が薄く、精査されると空欄が目立つ可能性。
- **選択肢B：利用者が管理する宛先にする**（推奨、ただし下記の弱点を認識した上で）。
  利用者自身が取得したドメインのサブアドレス（例：`d<乱数トークン>@利用者の実在ドメイン`）。
  既存の`canary_token.py`（HTTPSのURLを埋め込み、アクセスされたら操作者のWebhookが発火する
  設計）と同じ考え方をメールに応用できる＝ダミーが実際に使われた（スパム業者に送信された等）
  時の検知を兼ねる。電話番号は同様の「自分管理の着信」を用意するコストが高いため、電話は
  選択肢Aを既定にし、メールのみ選択肢Bを既定にする案を推奨する。
  - **独立レビューで判明した弱点（2026-10-09・正直に明記）**：選択肢Bは「1件ずつ精査される」
    ことへの耐性であり、「流出データ全体をまとめて集計される」ことへの耐性ではない。
    すべてのダミーのメールが同じドメインを指すため、`cut -d@ -f2 | sort | uniq -c` の
    ような単純なドメイン頻度集計一発で「1つのドメインに不自然に大量の行が集中している」
    ことが見え、ダミー候補の一括発見につながりうる。指示書の前提「盗んだ側は精査しない」
    は個々のレコードを疑って裏取りする手間を指すと解釈しているが、この集計は精査ではなく
    機械的な一発コマンドであり、その前提の範囲内かどうかは代表確認事項とする。
  - さらに台帳のID（record_hmac）をメールのローカル部にそのまま使わない設計にした
    （乱数トークンは乱数源のseedから決定的に導出され、台帳のHMACとは別物。台帳だけが
    流出してもメールと直接突き合わせられない。初期実装でIDを共用していたのを
    独立レビューで指摘され修正済み）。
- **選択肢C**：実在しないが形式上正しいダミードメイン（example.comなど）を使う。
  RFC 2606予約ドメインは「ダミーである」ことの手がかりになり、精査されると見分けの目印に
  なってしまう（指示書の「精査しない前提」の範囲内では問題にならないが、精査された
  場合の耐性は選択肢Bより弱い）ため推奨しない。
- 代表がBを選択（2026-10-13）。既定は `user-domain`、`--email-mode omit` で空欄に切替可。

## 7. 利用者ごとに生成を変える（Layer 1・Layer 2 共通）

- 入力：`--seed`（利用者固有の秘密値）と、生成する件数・対象市区町村。
- `random.Random(seed)`で決定的に生成。同じseedなら同じ出力＝再現性と「後から同じ
  ダミーを台帳なしで再認識する」ことの両立。
- 公開コードだけで一括除去されないようにする前提は「seedを知らなければ生成列を再現できない」
  ことに依拠する。Pythonの`random`はCSPRNGではない（将来的な解析で予測される可能性は
  ゼロではない）。**これは既知の限界として設計書に明記**し、高い安全性が要る用途では
  `secrets`ベースの鍵導出に変更する余地を残す（v1では`random.Random`で十分と判断：
  目的は「絶対に見破られない」ことではなく「精査しない攻撃者の手間を増やす」ことのため）。

## 8. データの再抽出と古いダミーの入れ替え

- 地番ポリゴン・公園/河川区域データは「生成した時点のスナップショット」。用途地域の変更
  （公園の指定解除等）で、過去に生成したダミーが将来いつか居住地になる可能性はゼロではない。
- 運用：`zee dilute refresh`相当のコマンドで、最新データを再取得し直し、既存ledgerの
  各地番が引き続き§1の判定を通るか再チェックする。通らなくなった地番のダミーは
  「失効」として台帳に印をつけ、利用者に再生成（古いダミーの入れ替え）を促す。
- 本v1プロトタイプでは判定ロジックの実装のみ（§10）。実データでの定期再抽出は
  G空間情報センターのUI手動ダウンロードが前提のため、完全自動化はできない
  （§1の確認できなかった点、参照）。

## 9. CLIの形（想定）

```
zee dilute generate \
  --city <市区町村コード or 名> \
  --parcels <登記所備付地図データの地番抽出ファイル> \
  --public-land <国土数値情報 都市公園+河川区域の抽出ファイル> \
  --abr-towns <アドレス・ベース・レジストリ 町字マスターCSV> \
  --zipcode-data <KEN_ALL.CSV or utf_all.csv> \
  --seed <利用者の秘密シード> \
  --count <生成件数> \
  --layer {fictional-town,real-nonresidential,both} \
  --email-mode {omit,user-domain} [--email-domain <利用者ドメイン>] \
  --out <出力ディレクトリ>  # records.csv + ledger.jsonl を書く
```

`--parcels` 等の入力ファイル形式はプロトタイプでは簡易JSON（実データのスキーマを
模したフィクスチャ、§10）。実データ投入時のパーサ（GML/シェープファイル読み込み）は
v1スコープ外とし、次フェーズで追加する（必要な外部ライブラリの要否を含め代表確認）。

## 10. プロトタイプの範囲

- 対象地域：フィクスチャ1件分（架空の「サンプル市」、実データではない）。
- 入力：`tests/fixtures/dilution/` 配下に、地番ポリゴン・公園ポリゴン・ABR町字マスター・
  郵便番号データの最小フィクスチャをJSON/CSVで同梱（実データではなく、実データと
  同じ列構成のダミー。この同梱フィクスチャ自体に実在住所は一切含まない）。
- 出力：`records.csv`（ダミーPIIレコード、見分ける目印なし）＋ `ledger.jsonl`
  （HMAC台帳、seedを鍵とする）。
- 空間結合はstdlibのみ（shapely等の追加依存なし。Zeeコア本体の「依存ゼロ」方針を継続）。
  判定は当初「候補ポリゴンの全頂点が公園/河川ポリゴンの内側」という頂点包含テストのみ
  だったが、**独立レビュー（社内4ペルソナ・Codex外部レビューの両方が独立に同じ欠陥を
  再現・2026-10-09）で「凹型（U字型等）の公園・河川区域では、全頂点が内側でも辺が
  くぼみを横切って外に出る地番を誤って合格させる」不健全性を指摘された**。河川区域は
  実データで典型的に長く曲がりくねった凹形状であるため、机上の懸念ではない。
  修正として、頂点包含に加えて「候補ポリゴンのどの辺も、公園/河川ポリゴンのどの辺とも
  交差しない」という辺交差テストを追加し、両方を満たした場合のみ合格とした
  （`tests/test_dilution.py::test_polygon_fully_inside_rejects_concave_escape` で
  U字形の再現ケースを回帰テスト化）。退行防止のため、フィクスチャだけでなく実データ
  投入前にも凹形状のケースで必ず再検証すること。
- **未対応（次フェーズへの申し送り・推測を含む）**：穴（池・中州等の内側に非公有地が
  存在するケース）を持つポリゴン、複数リングのポリゴンは今回のフィクスチャスキーマにも
  判定ロジックにも概念が無い。国土数値情報の公園・河川区域ポリゴンには実データで穴が
  存在しうる（推測：公式仕様書で穴の有無までは確認していない）。穴を無視すると、
  穴の内側（実は非公有地）にある地番を誤って「公有地に完全内包」と判定する恐れがある。
  実データ投入時に追加するGML/シェープファイルパーサは、穴付きポリゴンを検出し、
  （a）穴を含む公有地ポリゴンそのものを安全側で却下するか、（b）穴を判定に正しく
  組み込む、のどちらかを実装するまで、穴を持つ可能性のある実データを本機能に投入しない。

- **対応済み（2026-10-13・代表「進める」後の第一歩）**：入力スキーマに `holes` を持つ
  公有地ポリゴンは `load_public_land` が除外する（fail-closed。穴を正しく判定に組み込む
  (b) 案は実データパーサ導入時）。回帰テスト `test_load_public_land_drops_polygon_with_holes`。
- **設計の食い違い（要判断）**：§8 の refresh は「台帳の各地番を再チェック」だが、§5 の台帳は
  HMAC のみで地番を持たない。refresh には地番の保管場所（台帳外・seed で暗号化 等）が別途必要。

## 独立レビューの指摘と対応（2026-10-09）

実装後、社内4ペルソナレビューとCodex外部レビューを実施。高重大度の指摘は全て対応済み：
凹形状での誤判定（上記）／座標系(crs)が異なる地番データと公有地データを無警告で
突き合わせていた点（crs不一致を拒否するよう修正）／`国土数値情報`側の`kind`（公園・河川
以外）を無視して全ポリゴンを公有地扱いしていた点（park/river以外は除外）／Layer 2の
地番に紐づく町名がABR町字マスターと一度も照合されていなかった点（照合を追加）／
出力先を無警告で上書きし、再実行で過去の台帳が失われる経路（既存ファイルがあれば
拒否するよう修正）／`--seed`が空文字・短い文字列でも通り、HMAC鍵の強度を利用者任せに
していた点（最低16文字を強制、未指定時は設計書どおり自動生成）／メールアドレスの
トークンが台帳のID（record_hmac）をそのまま使っていた点・かつ`secrets.token_hex()`
由来で`--seed`を固定しても再現しなかった点（seed由来の乱数から決定的に導出する方式に
変更）。中重大度で明記に留めたもの：§6のドメイン集中リスク（上記）、fail-closedの
文言と実装の不一致（§2で訂正済み）。

レビュー後、完了報告の前に advisor（この実装とは別の視点でのチェック）でさらに2件発見・
即修正：(1) 町名が郵便番号データに一件もマッチしない時、固定の `--fallback-zip`
（既定 `"0000000"`）を全行に使い回していた＝これ自体が全Layer-1行に共通する
値レベルの目印（台帳無しでも`grep 0000000`で一括検出できる）だったため、同じ
郵便番号データセット内の実在の郵便番号をseed由来の乱数で選ぶ方式に変更
（`postal.py::zip_for_town`）。(2) 住所の衝突回避リトライ（同じ地番＋建物＋部屋番号が
再度引かれた場合に引き直す処理）が50回失敗すると、コメントの意図（重複を書かない）に
反して重複のまま書き込んでいた＝サイレントに失敗を握りつぶす経路だったため、
リトライが尽きたら生成を拒否する（Z809）ように修正。

## 目的判定（事前チェックへの回答）

- **問1**：この作業はZeeの目的カード(d)に明記の関門ではないが、Zee全体の目的
  「社会の不安を減らす」「盗まれるな・時間を稼ぐ」の具体化の一つであり、
  カード(c)の第4原則「他者の弱さを利益に変えない」（＝攻撃を収益源にする側の採算を崩す）
  に資する新しい防御手段。関門表には無い新規の探索であり、前には進めるが既存の関門
  （第三者skill審査・C1〜C5等）とは独立。
- **問2**：目的カード(b)「過剰主張をしない」「防御率の数値は出さない」は、この設計書・
  将来のREADMEの書き方で守る（§0・各所に明記）。「無害化はしない」方針とも矛盾しない
  （本機能は検知・反撃ではなく価値毀損のみ）。減らす操作は含まない（新規追加のみ）。
- **問3**：資産を残したまま同じ狙いを満たす代替は「混入せず警告文だけ出す」等だが、
  代表の狙い（採算を崩す）には直接効かないため不採用。本件自体が追加提案であり、
  既存資産を減らす選択は無い。
