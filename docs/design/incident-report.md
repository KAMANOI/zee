# 当局向け報告書の集約 — 設計書（指示書 2026-10-09）

> この文書・このブランチ（`feat/incident-report`）は代表の採否判断が出るまで `git push` しないこと。
> 既存方針（過剰主張をしない・確認済みと推測を分ける）をこの文書にも適用する。

## 0. 目的（指示書より）

囮・照会型カナリア・封じ込めで取れた記録を、事案ごとにまとめ、当局（警察／個人情報保護委員会）への通報・報告時に人が添える報告書として出力する。**提出操作はしない**（[[zee-incident-report-submission-manual-only-policy]]・2026-10-09代表指示）。民間が合法にできるのは相手を止めることではなく捕まえさせる材料を渡すことであり、本件はその材料づくりに範囲を限る（既存方針 [[zee-no-active-defense-report-to-authorities-policy]]）。

## 1. 入力の情報源（契約）— 着手前の確認結果

指示書が指す3つの仕組みのうち、**main にあるのは1つだけ**（2026-10-09時点）。

| 仕組み | 状態 | 本書が受け取る入力の形 |
|---|---|---|
| 封じ込め証跡エクスポート（20261001-0001） | **main に merge 済み**（`src/zee/telemetry/report_export.py`） | `zee export --out <prefix>` が書く `<prefix>.json`（`build_export()` のスキーマ：`events`・`active_containments`・`chain_verification`・`report_fields.incident_summary_auto`・`report_fields.affected_asset_ids`・`report_fields.detected_at_first/last`） |
| 照会型カナリア（20261009-0205） | **未merge**（`feat/query-canary`、代表の採否判断待ち） | 受け口（`examples/query_canary_http_receiver.py` / `query_canary_dns_receiver.py`）が書く hit ログ jsonl。共通フィールドは `ts`（ISO8601）・`remote_ip`・`token`。Zee本体（`events.jsonl`）には統合されていない（受け口は運用者が自分のインフラに置く別プロセスのため） |
| ダミー混入（20261009-0122 v2） | **未merge**（`feat/decoy-pii-dilution`、代表の採否判断待ち） | `ledger.jsonl`（HMAC台帳）そのものは**本書の入力にしない**（§5）。運用者が自分で `is_dummy()` を走らせた結果の集計（漏えいデータ件数・ダミー一致件数の2つの整数）だけを受け取る |

**設計判断**：本書は3つの仕組みの内部コード・ブランチには一切触れない（範囲外の指定どおり）。かわりに、各仕組みが**既に書き出しているファイル / 運用者が別途算出した集計値**を入力とする「ファイル契約」にする。これにより、後発2件がまだ代表の採否判断待ちで main に無いことと無関係に、本書は独立にテスト・レビューできる（フィクスチャで代替）。

未merge2件は**この時点では「採用するかどうか自体が未確定」**（`feat/query-canary`・`feat/decoy-pii-dilution` の設計書冒頭「代表の採否判断が出るまでpush禁止」）。本書はその採否を前提にせず、**採用された場合に出力ファイルの形が変わらない限り使える**契約として定義する。採否が変わればこの表の「状態」行を更新する。

## 2. 事案の束ね方（bundling）— 自動クラスタリングはしない

**確認済みの制約**：Zee は接続元IPを `events.jsonl` に記録しない（`containment-report-mapping.md` §5「アクセス元IPアドレス・ホスト名: 不明（Zeeはこの情報を記録しない）」）。ファイル囮・封じ込めの記録には、時刻・`asset_id`・`decoy_ref` 以外に相関させられる属性がない。これだけで「同一事案」を自動判定すると、無関係な2つの侵入を1件に混ぜる・同じ侵入を2件に割る、のどちらの誤りも起こしうる。

**設計判断（推測の自動化を避ける）**：事案の境界は**運用者が明示的に決める**。
- 封じ込め証跡は、運用者が `zee export --since <事案の開始> --until <事案の終了>` を実行した時点でその期間に絞られている（既存機能の再利用。新しいクラスタリングを実装しない）。
- 照会型カナリアの hit ログ・ダミー混入の集計値は、運用者が「この事案に属する」と判断したファイル／数値を `--canary-hits`（複数可）・`--dilution-leaked` / `--dilution-dummy-matched` で明示的に渡す。
- 本書のコードは、渡された入力をそのまま1つの事案として束ねるだけで、時刻・IP・トークンを使った自動マッチングは行わない。
- 出力には常に「この束ねは運用者が指定した範囲であり、Zeeが自動的に同一主体と判定したものではない」という注記を入れる（確認済みの事実と推測の分離。指示書補足3）。

複数の `--canary-hits` ファイルを渡した場合は、そのまま結合して件数・期間・トークン別集計を出す（結合自体は機械的な処理で推測を含まない）。

## 4. 出力の設計

### 4.1 宛先の切り替え（`--recipient {police,ppc}`）

1本のコードが共有するのは §1 の入力契約と `report_fields`（Zee提供データ）のみ。宛先ごとに**別のテンプレート関数**で組み立てる（`render_police()` / `render_ppc()`）。どちらも「Zeeが確認できる事実」「利用者が記入」「情報なし（Zeeは記録しない）」の三状態表記を使う（既存 `report_export.py` の `_OPERATOR_FILLS_IN` / `_ZEE_DOES_NOT_RECORD` パターンを再利用）。

宛先情報（URL・電話・受付時間）は §3 の表をコードの外（`src/zee/report/recipients.py` の定数テーブル、1件1件に `as_of` 日付と出典を持たせる）に置き、本文に直書きしない。利用者向けの注記として「窓口の名称・URL・受付時間は変わりうるため提出前に最新を確認してください」を両宛先共通で入れる。警視庁電話窓口の受付時間（平日8:30〜17:15）は警視庁の行にのみ付け、警察庁オンライン窓口・PPCには付けない（オンライン受付は時間外も申請自体は可能なため）。

### 4.2 ダミー混入の反映（本人の数の補正材料）

運用者が `--dilution-leaked N --dilution-dummy-matched D` を渡した場合のみ、PPC宛て報告書の「本人の数」欄に「漏えいデータ N 件中 D 件がダミー判定（運用者側で台帳突き合わせ済み）→ 実在の本人数は **N−D 件以下**」という材料を追加する。これは上限の補正であり確定数ではないため、「本人の数」の最終記入は利用者が行う、という既存の三状態表記を崩さない。

**ledger.jsonl・seed は本書のコードに一切渡さない・読み込まない**（§5）。渡すのは運用者が既に計算した2つの整数だけであり、台帳のHMAC・seedという「ダミーを見分ける手段そのもの」は報告書生成の経路に乗らない。報告書に書くのは「ダミー判定は別途提示可能」という一文のみ。

### 4.3 照会型カナリアの反映

`--canary-hits <path>`（複数可）で渡された jsonl を読み、件数・最初/最後の発火時刻・一致した `token` の数（ユニーク）を集計する。`remote_ip` はログに**そのまま転記する**（Zeeが生成した値ではなく運用者の受け口が記録した値であり、報告書の性質上そのまま出す必要がある）。hostname型（DNSのみ）の場合、記録されているのは攻撃者の機材ではなく再帰DNSリゾルバのIPである可能性が高いという限界（`query-canary.md` §2.1）を、報告書の注記にそのまま引用する（過剰主張をしない）。

### 4.4 出力形式 — PDF依存は追加しない

`pyproject.toml` の `dependencies = []`（コアは依存ゼロ方針）に合わせ、新規の外部ライブラリ（`fpdf2`/`reportlab`/`weasyprint` 等）は**追加しない**。出力は既存の `render_text()` と同じ stdlib のみの方式で、

- `<out>.json`（全データ）
- `<out>.txt`（既存 `render_text` と同じ形の全文）
- `<out>.html`（stdlib の文字列組み立てのみ・外部CSS/フォント読み込みなし。ブラウザの「印刷→PDFで保存」で誰でもPDF化できる）

の3点を書く。直接PDFを生成する依存追加の可否は代表判断（PENDING）。

### 4.5 自動送信はしない（コードで保証）

本モジュールの import グラフに `urllib` / `http.client` / `socket` / `smtplib` / `requests` のいずれも含まれず、`zee.notifier` も import しないことをテストで保証する（§7 テスト3）。ネットワークに触れる手段を物理的に持たない設計であり、「しない方針」だけでなく「できない実装」にする。

## 5. セキュリティ設計（design-workflow Phase 4 の5点）

リポジトリに `docs/SECURITY_DESIGN.md` は存在せず、既存の `docs/threat-model.md` がその役割を担っている（Zee全体を書き直す改修は本件の範囲外）。本件固有の5点はここに記す。

1. **データ台帳**：入力ファイル（export JSON・canary-hits jsonl）はローカルパスから読むだけで複製・保存しない。出力（json/txt/html）は `zee export` と同じ `_write_private_files` ヘルパーで 0600・排他作成（既存コード再利用）。ledger.jsonl・seedは読み込まない（§4.2）。保持期間・削除は運用者の責任（Zeeは「持たない」が既定＝生成後の管理は外）。
2. **信頼境界**：新しい入口は CLI 引数（ファイルパス・整数2つ・宛先選択）のみ。外部ネットワーク入力はない。渡されたJSONの形式が壊れていれば読み取りエラーとして拒否する（Z10xx、§6）。
3. **脅威モデル**（最低5件）：
   - ①壊れた/改変されたcanary-hitsファイルを渡される→ JSONDecodeError を拒否（握って握り潰さない）。
   - ②`--dilution-dummy-matched` が `--dilution-leaked` を超える矛盾した入力→ 検証して拒否（Z10xx）。対策が効かない条件：運用者が意図的に誤った数字を入れた場合は検出できない（Zeeは運用者の集計の正しさまでは保証しない）。
   - ③出力ファイルの誤上書き→ 既存の `_write_private_files`（非上書き既定・`--force`必須）を再利用。
   - ④報告書に機微情報（ledger・seed）が紛れ込む→ §4.2の設計で経路自体を断つ（構造的対策）。
   - ⑤宛先指定ミスで警察向けテンプレートにPPCの法定9項目が混ざる（逆も）→ `--recipient` は `{police,ppc}` の2値のみ受け付け、それ以外は Z10xx で拒否。テンプレート関数も完全に分離（§4.1）。
   - 対策が効かない既知の限界：Zeeは接続元を記録しないため「同一攻撃者か」の判定は常に運用者の推測（§2）。
4. **秘密と実行権限**：新しい鍵・認証情報は追加しない。実行はローカルCLIのみ（AIエージェントが代行する実行範囲は「ファイル読み込み・ローカル出力」に限られ、提出操作は含まない＝§4.5）。
5. **公開前基準との照合**：本機能は新規データ収集・新規ネットワーク入口を持たないため、既存 `docs/threat-model.md` の記載に矛盾しない。公開（push）は代表の採否判断後。

## 6. エラーコード

既存 `errors.py` の `Z8xx` は `feat/decoy-pii-dilution`（未merge）が既に割り当てているため衝突を避け、新しいレンジ `Z10xx` を追加する（本書のブランチでのみ）。

- `Z1001_UNKNOWN_RECIPIENT`：`--recipient` が `police`/`ppc` 以外
- `Z1002_INVALID_CANARY_HITS_FILE`：canary-hitsファイルが存在しない、またはJSONLとして読めない
- `Z1003_DILUTION_COUNT_INCONSISTENT`：`--dilution-dummy-matched` が `--dilution-leaked` を超える、または負の値
- `Z1004_EXPORT_FILE_REQUIRED`：`--export-json` が未指定、または `build_export()` のスキーマ（`schema_version`）と一致しない

## 7. 検証基準（Phase 5）

1. `tests/test_incident_report.py` が全てパスすること。
2. フィクスチャ（export JSON 1件＋canary-hits 2件＋ダミー集計）から事案を束ね、`--recipient police` と `--recipient ppc` で出力の宛先欄・法定9項目ブロックの有無が切り替わること。
3. 本モジュールの import グラフに `urllib`/`http.client`/`socket`/`smtplib`/`requests`/`zee.notifier` のいずれも含まれないこと（`ast` でソースを静的解析するテスト）。
4. 改ざん検知情報（`chain_verification`）がそのまま報告書に転記されること。
5. 壊れたcanary-hitsファイル・矛盾したdilution数値・不正な`--recipient`がそれぞれ対応するZ10xxで拒否されること。
6. 出力ファイルに提出・送信を行うコードパスが存在しないこと（4で確認）＋ `_write_private_files` 経由で0600・非上書きで書かれること。

## 目的判定（事前チェックへの回答）

- **問1**：Zeeの目的カード(d)に明記の関門ではないが、指示書・カード(c)の方向性（第5原則「自己実現と社会貢献を分けない」・第6原則「個を越えて繋がる」＝記録を当局へ渡す形で社会につなぐ）に資する新しい出力レイヤーの追加。既存の関門（第三者skill審査等）とは独立。
- **問2**：目的カード(b)「無害化はしない」「過剰主張をしない」は、本書が自動送信経路を持たない設計（§4.5）・宛先ごとの確認済み/推測の分離（§3-4）で守っている。減らす操作は含まない（新規追加のみ、既存3仕組みのコードは無変更）。
- **問3**：資産を残したまま同じ狙いを満たす代替＝「報告書を自動生成せず、運用者が毎回手で各出力を読んで転記する」案があるが、指示書の目的（速やかな提出への移行）に直接効かないため不採用。本件自体が追加提案であり、既存資産を減らす選択はない。
