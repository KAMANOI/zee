# 当局向け報告書の集約（`zee incident-report`）— 設計書

> 方針：過剰主張をしない・確認済みと推測を分ける。

## 0. 目的

囮・封じ込めで取れた記録を事案ごとにまとめ、当局（警察／個人情報保護委員会）への通報・報告時に人が添える報告書として出力する。**提出操作はしない。** 民間が合法にできるのは相手を止めることではなく、捕まえさせる材料を渡すことであり、本機能はその材料づくりに範囲を限る。

## 1. 入力の情報源（契約）

入力は1つだけ：`zee export --out <prefix>` が書く `<prefix>.json`（`src/zee/telemetry/report_export.py` の `build_export()` のスキーマ）。

本機能は `zee export` の内部コードには触れず、**既に書き出されたファイル**を入力とする「ファイル契約」にする。これにより本機能は独立にテスト・レビューできる。

入力ファイルは**非信頼**として扱う（手で編集された・壊れたファイルを渡されうる）：

- `load_export()` が、使う項目の存在と型を検証する：`schema_version`（文字列・対応版）、`redacted`・`events_truncated`（真偽値）、`events_total`・`events_included`（0以上の整数。真偽値は不可）、`events`・`active_containments`（リスト）、`chain_verification`（`events_jsonl` / `metrics_jsonl` の `status` が文字列）、`report_fields.incident_summary_auto`（文字列）、`report_fields.detected_at_first/last`（文字列または null）、`report_fields.affected_asset_ids`（文字列のリスト）。**欠落・型違いは Z1004 で拒否し、既定値（0件など）で補完しない。**
- `events` と `active_containments` は、**既知の項目だけを許可リストで転記する**（events：`schema_version`・`event_id`・`timestamp`・`source`・`confidence`・`op_class`・`asset_id`・`decoy_ref`・`detail`／active_containments：`asset_id`・`method`・`cut_at`・`platform`・`modified`）。それ以外の項目は報告書に入らない。
- 報告書の本文（txt/html）に入る外部由来の文字列（export内の文字列・`--incident-label`）は、C0/C1 制御文字（改行を含む）と U+2028/U+2029 を `\n`・`\r`・`\t`・`\uXXXX` の形で見えるようにしてから出す。改行を差し込んで偽の見出しや行を作ることはできない。
- 元の export の `redacted` を報告書に引き継ぐ。`--no-redact` で作られた export（パスが伏せられていない）の場合は、txt/html の冒頭に注記を出し、生成時に標準エラーにも警告を出す。

## 2. 事案の束ね方（bundling）— 自動クラスタリングはしない

**確認済みの制約**：Zee は接続元IPを `events.jsonl` に記録しない（`containment-report-mapping.md` §5「アクセス元IPアドレス・ホスト名: 不明（Zeeはこの情報を記録しない）」）。ファイル囮・封じ込めの記録には、時刻・`asset_id`・`decoy_ref` 以外に相関させられる属性がない。これだけで「同一事案」を自動判定すると、無関係な2つの侵入を1件に混ぜる・同じ侵入を2件に割る、のどちらの誤りも起こしうる。

**設計判断（推測の自動化を避ける）**：事案の境界は**利用者が明示的に決める**。

- 封じ込め証跡は、利用者が `zee export --since <事案の開始> --until <事案の終了>` を実行した時点でその期間に絞られている（既存機能の再利用。新しいクラスタリングを実装しない）。
- 出力には常に「この束ねは利用者が指定した範囲であり、Zeeが自動的に同一主体と判定したものではない」という注記を入れる（確認済みの事実と推測の分離）。

## 3. 報告の相手（警察／個人情報保護委員会）— 一次資料の確認結果

一次資料を確認した（公式サイトの取得、e-Gov 法令API v2 での条文の直接取得）。確認できなかった項目は「未確認」。

| 項目 | 条文の内容 | 確度 |

**Zeeがこの事案に関して「不正アクセス等（第3号類型）」の材料をどこまで示せるか**：囮の発火は「何者かが不正にデータへアクセス・処理した」ことの技術的な証跡ではあるが、それが施行規則第7条第3号の法的な該当性を満たすかどうかの判断は利用者が行う（Zeeは判定しない）。報告書には「60日/30日のどちらが適用されるかは利用者が判断」の注記を必ず入れる。PPC宛ての「4 原因」欄には、検知イベントがある場合に限り「囮の検知イベントの記録あり（該当性の判断は利用者）」とだけ書く。「3 本人の数」は Zee が持たない情報のため「利用者が記入」とする。

### 3.3 警察とPPCの手続きの違い

法的根拠・窓口・フォームがそれぞれ別（警察＝e-Gov経由npa.go.jp、PPC＝roueihoukoku.ppc.go.jp）であることは確認できたが、「両者が別の法的手続きである」と一文で明言する一次資料そのものには到達できなかった（構造的な分離は確認済み、明文の言明は未確認）。報告書は両者を同一の文書で混同して扱わない設計とする（§4）。

## 4. 出力の設計

### 4.1 宛先の切り替え（`--recipient {police,ppc}`）

本文は選んだ宛先1件分の項目だけを並べる。どちらも「Zeeが確認できる事実」「利用者が記入」「情報なし（Zeeは記録しない）」の三状態表記を使う（既存 `report_export.py` の `_OPERATOR_FILLS_IN` / `_ZEE_DOES_NOT_RECORD` パターンを再利用）。末尾には参照窓口として警察・PPCの両方を常に載せ、両者が別の手続き・別の期限であることを明記する。

宛先情報（URL・電話・受付時間）は §3 の表をコードの外（`src/zee/report/recipients.py` の定数テーブル、1件1件に `as_of` 日付を持たせる）に置き、本文に直書きしない。利用者向けの注記として「窓口の名称・URL・受付時間は変わりうるため提出前に最新を確認してください」を両宛先共通で入れる。警視庁電話窓口の受付時間（平日8:30〜17:15）は警視庁の行にのみ付け、警察庁オンライン窓口・PPCには付けない（オンライン受付は時間外も申請自体は可能なため）。

### 4.2 出力形式 — PDF依存は追加しない

`pyproject.toml` の `dependencies = []`（コアは依存ゼロ方針）に合わせ、新規の外部ライブラリ（`fpdf2`/`reportlab`/`weasyprint` 等）は**追加しない**。出力は stdlib のみで、

- `<out>.json`（全データ）
- `<out>.txt`（人が読む全文）
- `<out>.html`（stdlib の文字列組み立てのみ・外部CSS/フォント読み込みなし。ブラウザの「印刷→PDFで保存」で誰でもPDF化できる）

の3点を書く。

### 4.3 自動送信はしない（コードで保証）

本モジュールの import グラフに `urllib` / `http.client` / `socket` / `smtplib` / `requests` のいずれも含まれず、`zee.notifier` も import しないことをテストで保証する（§7 テスト3）。ネットワークに触れる手段を持たない設計であり、「しない方針」だけでなく「できない実装」にする。

## 5. セキュリティ設計

全体の脅威モデルは `docs/threat-model.md`（「Evidence store and containment export」節に本機能の行がある）。本機能固有の点はここに記す。

1. **データ**：入力ファイル（export JSON）はローカルパスから読むだけで複製・保存しない。出力（json/txt/html）は `zee export` と同じ `_write_private_files` ヘルパーで 0600・排他作成。保持・削除は利用者の責任。
2. **信頼境界**：新しい入口は CLI 引数（ファイルパス・宛先選択・ラベル）のみ。外部ネットワーク入力はない。入力ファイルは非信頼として扱う（§1）。
3. **脅威と対策**：
   - ①壊れた/改変された export を渡される → 形式・型を検証して Z1004 で拒否（欠落を補完しない）。
   - ②export に余計な項目（個人情報・秘密）が紛れ込んでいる → events / active_containments は許可リストの項目だけ転記。
   - ③文字列に改行・制御文字を入れて偽の見出しを作る → 本文に出す前に見える形へエスケープ。
   - ④出力ファイルの誤上書き → `_write_private_files`（非上書き既定・`--force`必須）。出力先が入力と同じパスなら `--force` でも拒否（Z1005）。
   - ⑤`--no-redact` の export からパスが報告書に載る → 報告書と標準エラーで明示（載ること自体は止めない。利用者の選択のため）。
   - ⑥宛先指定ミスで警察向けにPPCの法定9項目が混ざる（逆も） → `--recipient` は `{police,ppc}` の2値のみ受け付け、それ以外は拒否（argparse／ライブラリ経由では Z1001）。
   - 対策が効かない既知の限界：Zeeは接続元を記録しないため「同一攻撃者か」の判定は常に利用者の推測（§2）。`asset_id` はマスクされない。
4. **秘密と実行権限**：新しい鍵・認証情報は追加しない。実行はローカルCLIのみで、提出操作は含まない（§4.3）。

## 6. エラーコード

新しいレンジ `Z10xx` を追加する。

- `Z1001_UNKNOWN_RECIPIENT`：`--recipient` が `police`/`ppc` 以外（CLI では argparse が先に拒否する。`build_incident_report()` を直接呼んだ場合に出る）
- `Z1004_EXPORT_FILE_REQUIRED`：`--export-json` のファイルが `zee export` が書くスキーマと一致しない、または読めない
- `Z1005_OUTPUT_COLLIDES_WITH_INPUT`：`--out` の出力先が `--export-json` の入力ファイルと同じ（`--force` でも上書きしない）

## 7. 検証基準

1. `tests/test_incident_report.py` が全てパスすること。
2. `--recipient police` と `--recipient ppc` で出力の宛先欄・法定9項目ブロックの有無が切り替わること。
3. 本モジュールの import グラフに `urllib`/`http.client`/`socket`/`smtplib`/`requests`/`zee.notifier` のいずれも含まれないこと（`ast` でソースを静的解析するテスト）。
4. 改ざん検知情報（`chain_verification` の status）が報告書に転記されること。
5. 壊れた export（欠落・型違い）が Z1004 で拒否されること。改行注入で偽の見出しが出ないこと。未知の項目が転記されないこと。`--no-redact` 由来の export が明示されること。
6. 出力ファイルに提出・送信を行うコードパスが存在しないこと（3で確認）＋ `_write_private_files` 経由で0600・非上書きで書かれること。
