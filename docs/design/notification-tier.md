# Zee 通知の影響段階表記 — 設計書

## 背景
情報の機微性・業務への影響・波及範囲の3軸で段階を決める、一般的な考え方を借用する。段階名・閾値・判定ルールはZee独自に設計する。

対象ユーザー: 専門の担当者がいない中小企業。通知を見た瞬間に「これはどれくらい深刻か」が分かることを目的にする。

## 設計原則（必須）
1. **自動封じ込めの判定には一切使わない。** `sequence.py` の mode 解決（`policy/asset_profile.resolve`）・confidence ゲート・`op_class=="change"` ゲート・dry_run 分岐は本機能の前後でコード上無関係のまま変更しない。段階の計算が例外を出しても、あるいは本機能自体を削除しても、`ResponderResult.cut_executed` / `cut_would_have_been_executed` / `cut_skipped_reason` / `mode` は変わらない。
2. 使ってよい場所は表示だけ: `notify_local` に渡す title/body、webhook payload。
3. **置かない場所**: `event_log.record_event()` / `telemetry/report_export.py` / `zee export` の出力。証跡エクスポートの報告項目は当局の一次資料で確定させる別仕様の領域であり、本機能はそれを置き換えない。人が読む要約（通知）として別に持つだけ。

## 3軸の定義

### 軸A 機微性（0=低 / 1=中 / 2=高）
入力: `event.decoy_path`（内部計算にのみ使い、通知にはカテゴリ名だけを出す。生パスは出さない — `sequence.py` 既存コメントが decoy_ref を使う理由と同じ配慮）。

判定:
1. `decoy_path` が `None` → 0。カテゴリ名「パス種別不明」、reason には「パス種別は未確認」と書く（取れた軸だけで判定する方針どおり）。
2. `zee.decoy.seeder._pick_template(path)` が `credentials` / `env` / `ssh_key` のいずれか → 2、カテゴリ名「認証情報・鍵」。**既存の囮テンプレート判定をそのまま再利用する**（同じ判定を新規に書かない）。
3. ファイル名が個人情報語リスト `{顧客, customer, personal, 患者, 名簿, member}`（いずれかを部分一致・小文字化して比較）に一致 → 1、カテゴリ名「個人情報を含みうるデータ」。
   - 注記：部分一致のため粗い判定である（例：`member` は `remember.txt` にも一致する）。表示だけの段階であり封じ込めには使わないため、この粗さは許容する。
4. それ以外（`_pick_template` が `notes` を返す場合を含む） → 0、カテゴリ名「一般ファイル」。

### 軸B 権限（0=低 / 1=中 / 2=高）
「共通の管理権限や、他の利用者・他システムに及ぶ認証に関わるか」。入力: 軸Aの結果 + `asset.type`。

| asset.type | 軸A=認証情報・鍵(2) | 軸A≠認証情報・鍵 |
|---|---|---|
| workstation | 1 | 0 |
| server / ot | 2 | 1 |

根拠: 認証情報・鍵はそれ単体で他システムへの認証に関わり得るため、資産が workstation 単体でも 0 にはしない。server/ot は複数利用者・複数システムが依拠する共有基盤という既存の `AssetType` 設計（`config/schema.py`）をそのまま信号として使う。

### 軸C 業務波及（0=低 / 1=中 / 2=高）
「封じ込め対象の量、共有領域か、業務で使う領域か」。3つの真偽シグナルの成立数で決める（0〜1→0、2→1、3→2）:
- 件数シグナル: `len(asset.decoy_paths) >= 3`（この資産に設定された囮の総数。今回検知した1件の数ではない）
- 共有領域シグナル: `asset.type != "workstation"`
- 業務領域シグナル（**近似値**。assets.toml に厳密な「業務用途」フラグが無いための代替指標であることを明記する）: `asset.overnight_active`

## 段階（4段階、独自命名）
1. 情報
2. 注意
3. 警戒
4. 重大

計算:
```
max_level  = max(軸A, 軸B, 軸C)
high_count = (軸A==2) + (軸B==2) + (軸C==2)

if high_count >= 2:   level = 4  # 重大 — 複数軸が同時に高い
elif max_level == 2:  level = 3  # 警戒 — 1軸が高い
elif max_level == 1:  level = 2  # 注意
else:                 level = 1  # 情報 — 全軸が低い
```

### op_class との整合（表示だけの補正・必須）
段階は「本物だった場合の影響」、`op_class`（read/change）は「本物らしさ・疑わしさ」で、別の軸である。既存の `_hint_for("change")` は本文で「危険度が高い可能性があります」と書く。数字の段階（例: 情報）と本文の文言（危険度が高い）が矛盾して見えないよう、**`op_class == "change"` のときは表示段階の下限を2（注意）にする**（計算結果が1ならその通知に限り2へ上げる。3軸の判定自体やログに残す軸の値は変えない。表示用の最終値だけの補正）。

## 判定理由1行
テンプレ: `{機微性カテゴリ}のパスへの{動作}を{検知/封じ込め/手動確認待ち}。{確認できた軸の短い説明}`

- **数量は書かない。** 1イベント=1囮であり、「対象Nファイル」という表現は実際より広く見える（過剰主張になる）。件数は軸Cの内部入力にのみ使い、表示しない。
- **パスの実体（ファイル名・ディレクトリ名）は書かない。** カテゴリ名だけ。
- 動作語は通知の文脈で変える（設計原則「段階表記は表示層だけ」を reason 行でも守る。封じ込めが実際に起きていない通知で「封じ込め」と書かない）。新しい通知を追加するのではなく、既存の3箇所の `notify_local` 呼び出しにそれぞれ付ける:
  - step1（cut判定前の通知。mode/dry_run に関わらず常にこの時点では「検知」): 「検知」
  - dry_run で cut は実行しない（実行していたはずの）場合の通知: 「検知（dry_run、手動確認可）」
  - 実際に cut を実行した後の通知: cut 関数が成功を返した場合のみ「封じ込め」。失敗を返した場合（権限不足等）は「遮断を試行(失敗、手動確認が必要)」。成功したかのように断定しない。
  - mode!=contain や op_class=read で cut されない場合は追加の通知自体が無い（既存どおり）。手動確認待ちの意味は既存の `_hint_for` 本文がすでに説明しており、reason 行で重複させない。
- 確認できた軸の説明は確認できたものだけ列挙する（例: 「資産は共有領域」「資産は単一ワークステーション」「夜間も稼働」「パス種別は未確認」）。`overnight_active` が偽の資産に「常時稼働」と書かない（共有かどうかと夜間稼働かどうかは別の事実であり、確認できていない方を書かない）。
- カテゴリ名は冒頭の `{機微性カテゴリ}のパスへの接触を…` で既に出ているため、確認できた軸の説明では重複させない（「種別: 認証情報・鍵」のような繰り返しは書かない）。例外: パス種別が未確認の場合は冒頭が「パス種別不明」になるため、「パス種別は未確認」の説明を別途加える。
- 遮断を試行して失敗した場合（`contain_failed`）は「{機微性カテゴリ}のパスへの接触を検知。遮断は失敗(手動確認が必要)。{確認できた軸}。」という文型にする（「…を遮断を試行」のような「を」の連続を避ける）。

## 失敗時のフェイルクローズ
`classify()` が例外を出した場合、`tier.safe_classify()`（`sequence.py` はこれだけを呼ぶ）で捕捉し、最低段階（1 情報）＋ reason「種別を確認できず最低段階で表示」にフォールバックする。これは「判定不能」という別区分ではなく、「確認できた軸が0個」という既定ルールの縮退形。封じ込め判定（gate）は一切変更しない（設計原則1）。

## テスト方針
1. 既存の全テストが通ること。
2. **段階表記の有無で封じ込めの動作が変わらないことの確認**:
   - a. `classify()` を4段階それぞれに固定するモンキーパッチで `handle()` を呼び、`cut_executed` / `cut_would_have_been_executed` / `cut_skipped_reason` / `mode` が段階に関わらず同一であることを確認する。
   - b. `classify()` が例外を出すようにモンキーパッチして `handle()` を呼び、step1 の `notify_local` は実行され、cut の結果は (a) と同一であることを確認する。
3. 軸A/B/C、4段階マッピング、op_class 下限補正、reason 行それぞれの単体テスト。

## 公開して良いか
本プロジェクトは「公開物にトラップの作動条件・閾値・方式を書かない」方針を取る。これは囮の**検知ロジック・発火閾値**を指す。本機能は検知が成立した**後**の表示の重み付けであり、対象が異なる。本設計書の数値（軸の閾値・段階マッピング）を公開しても、トラップが作動する条件そのものは何も明らかにしない。公開して良いと判断する。
