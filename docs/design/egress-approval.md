# 設計案：持ち出し承認 — 保護データの外部送信を、別端末の署名が出るまで通さない

状態：設計案＋macOS試作。main に統合済み（2026-10-11）。**未配線**（`zee watch`・CLI・通知・実ファイアウォールからは使われない）・既定OFF。リリースには含めていない。
作成：2026-10-11
配置：`design/key-watch` が `docs/design/` を使っているので、それに従った。

> 特定マシンの鍵の所在・宛先一覧はここに書かない（公開リポジトリ。攻撃者の地図になる）。
> 「確認済み」は作者がリポジトリ・開発機（macOS）で実際に見たもの、「推測」は見ていないもの。

## 0. 先に読む：Zee の哲学との関係

Zee は「侵入を防ぐ」道具ではなく「侵入後に封じ込めて時間を稼ぐ」道具。この機能も同じ側に立つ。
**止められるのは「承認の無い宛先への、承認前に検知できた分以降の送信」まで。最初の数秒に出た分は戻せない**
（§7・§10）。「持ち出しを防ぐ」とは書かない。既定は OFF（観察のみ）で、利用者の明示操作で ON になる。

## 1. 判定条件：何を「持ち出しの形」とみなすか

全送信に承認を挟むのは成り立たない（OS の常時通信、無人サーバー、承認疲れ）。次の**どれか**に当たる送信だけを
「持ち出しの形」とし、普段の通信は止めない。許可リストにある宛先は常に素通し（loopback は暗黙の許可）。

| # | 形 | PC | サーバー |
|---|---|---|---|
| A | 許可リスト外の宛先 かつ 保護対象に触れてから `TAINT_WINDOW`（既定10分）以内 | ○ | — |
| B | 許可リスト外の宛先 かつ 1サンプルの送信量が `BYTES_THRESHOLD`（既定1MB）以上 | ○ | — |
| C | 許可リスト外の宛先であれば何でも | — | ○（許可リスト主義） |

- **保護対象**＝`watch_paths ∪ decoy_paths`。定義は `design/key-watch` と共通にする（未マージ。マージ前は
  エンジン内の `protect` 一覧に手で入れる＝試作）。
- 「触れた」の入力は既存 watcher のイベント。**macOS の kqueue は読み取りを報告しない**（確認済み・README の
  能力表）。よって macOS の A は「変更・改名・削除」か「canary の発火」でしか立たない。**読み取りだけの持ち出しは
  A では捕まらず、B（量）に頼る**。これは言い切る限界。
- **送信元プロセスを特定できない環境での代わり**：プロセス名を判定条件に使わない。判定は「宛先」「量」「保護対象に
  触れた時刻」だけ。プロセス名は承認画面の表示と証跡のための付帯情報（macOS では下記サンプリングで得る）。
- 宛先と量の取得（macOS・権限不要・**確認済み**）：`lsof -nP -iTCP -sTCP:ESTABLISHED -F` が自ユーザーのプロセスの
  接続（プロセス↔宛先）を返す。`nettop -P -L 1 -x -J bytes_in,bytes_out` はプロセス別の累積バイトを返すが
  **宛先は返さない**。両者を pid で突き合わせて「プロセス・宛先・差分バイト」にする（サンプリング間隔内の誤差あり）。
  他ユーザー・root のプロセスは見えない（推測：lsof の通常の権限挙動）。
- **無人ジョブが動く機械の注意**：無人の自動実行（launchd 等）が秘密ファイルに触れ、多数の外部APIを呼ぶ機械では、
  A は「触れた後の**新しい**宛先」だけを数えるので、**ON にする前に最低14日の観察（学習）期間を置き、実際に使う
  宛先を許可リスト候補として一度の署名承認で入れる**。これを飛ばすと業務が止まる。

## 2. PC の形とサーバーの形

承認の仕組み（鍵・台帳・許可リスト・署名検証）は共通。違いは判定と、承認者不在時の扱い。

| | PC（人が操作） | サーバー（無人） |
|---|---|---|
| 判定 | 形A・B（相関） | 形C（許可リスト主義） |
| 強制手段 | 該当宛先の pf ブロック（root 要）。無ければ通知のみ | 既定拒否の pf/nft＋署名で追加される通し先リスト |
| 承認者が不在 | 保留のまま。**応答が無ければ通さない** | 同じ。**応答が無ければ通さない**。許可リスト内の通信は影響なし |
| 実装 | macOS 試作（本書） | **設計まで。Linux 実装は第2段** |

PC で既定拒否にしないのは、OS とアプリの通信が壊れるため（推測：実測していない）。サーバーは通信先が有限で、
許可リストを完成させられるので既定拒否が成り立つ。既存の egress 遮断で自動遮断後も RFC1918・IPv6 宛てが通る点は、
サーバー形では「RFC1918 を暗黙に許さない・IPv6 も同じ表で扱う」ことで吸収できる（`pf.render` は IPv6 を扱う）。


## 3. 要件（1）〜（6）をどう満たすか

**（1）同期しない鍵。** 承認鍵は端末から取り出せない鍵を使う。登録時に `custody` を申告させ、台帳に残す：
`hardware-key`（FIDO セキュリティキー）／`secure-enclave-app`（自作アプリ）／`synced-passkey`（iCloud 等で同期）。
`synced-passkey` は**使えるが「同期先アカウントが落ちれば承認鍵も落ちる」ことを導入時に表示**し、予備鍵（別の custody）
が無いと ON にできない。Secure Enclave は P-256 のみ・非エクスポート（Apple 開発者フォーラム等の二次情報、公式一次は未確認）。
→ 署名は P-256/ES256 に固定した。試作：`custody` 欄は**未実装**（鍵の公開鍵のみ保持）。

**（2）登録とリカバリー。**
- 最初の1台だけはホストのコンソールで登録（`bootstrap_key`）。**2台目以降の追加・削除は登録済み端末の署名が無いと通らない**
  （`key_add`/`key_remove`。最後の1台は消せない。ON 中に2台未満になる削除は、単独運用の承認（`ack_single_key`）が無い限り請求の発行自体を拒否し、承認の適用時にも最新の台帳で再検査する（`would_leave_one_key`。3台の時に発行した削除2件を順に承認しても1台にはならない）。壊れた状態ファイルのもとでは、署名なしの初回登録（`bootstrap_key`）も拒否する。
- `enable()` は予備鍵（2台目）が無いと拒否。単独運用は `ack_single_key()` を明示し証跡に残す。
- **全鍵喪失**：`recovery_start` → **72時間待機**（`RECOVERY_WAIT`）→ `recovery_complete` で保留中の遮断と承認済みの許可をすべて解除し（`disable` と同じ処理）、台帳を空にして OFF に戻る。解除が1件でも失敗したら何も消さずに `release_failed` を返す（再実行で続きから）。
  待機中は6時間ごとに通知を出し続け（`recovery_pending`）、登録済み端末の署名付き**設定変更（config）**が1回でも通れば取り消される（送信承認では取り消されない）。
  ※ 同一ユーザー権限の攻撃者は `recovery_start` を打てる。狙いは「静かにはできない」こと（通知＋証跡）。
- ヘルプデスク経由の登録は存在しない（個人運用の道具のため）。

**（3）検証側の実装。** 検証は Zee 自身。`Engine.submit` が次を**すべて**要求する：(a) Zee 自身が発行した請求に対する
応答（`unknown_request`）、(b) 期限内（`expired`）、(c) 署名対象の全項目が発行した請求と一致（`payload_mismatch`）、
(d) 照合コードの一致（`code_mismatch`）、(e) 登録済みの鍵（`unknown_key`）、(f) 同じ署名の再使用でない
（`replay`。使用済みダイジェストをディスクに保存してから承認を実行する）、(g) 署名が有効（`bad_signature`）。**照合コードの一致（`code_mismatch`）は署名検証の後**に見る（登録鍵を持たない者が00〜99を総当たりしても何も分からない。レビューで実測した穴を塞いだ）。型が不正な入力は例外にせず `malformed`。
請求の nonce は16バイト乱数で、請求は一度使うと消える。実運用では「請求は一度で消える」が主な防御で、ディスク上の使用済み台帳は再起動をまたぐ二重の保険。単一プロセス前提（状態の読み込みは起動時1回。複数プロセスの同時書き込みは未対応）。署名対象は
`SHA-256("zee-egress-approval-v1\0" ‖ 正準JSON(請求全体＋入力コード))`（`signing.payload_digest`）。

**（4）設定変更も署名対象。** 許可リストへの宛先追加（`allow_add/remove`）、保護対象の変更（`protect_add/remove`）、
持ち出し承認の停止（`disable`）、承認端末の追加・削除（`key_add/remove`）は `kind=config` の請求として発行し、
送信承認と同じ検証を通す。操作ごとの必須引数（空でない文字列）は請求の発行前に検査し、不正なら請求を出さない。`allow_add` が適用されると、追加した条件（CIDR・`*.` を含む）に一致する保留中の宛先は遮断を解除する。ON の間は署名なしのローカル変更手段が**存在しない**（`setup_*` は OFF の間だけ。試作で検証）。
※ ただし状態ファイルを直接書き換えられる同一ユーザーの攻撃者には効かない（§10）。

**（5）見せた内容と通す通信の一致。** 署名対象に宛先一覧・プロセス名・量の上限（`max_bytes`）・対象データの識別・
期限（`exp` 応答期限、`until` 許可の終端）・nonce が入る。通すのは `dests` に載った宛先に、`max_bytes` の範囲で
`until` まで。超えたら再び保留（試作で検証）。承認済みの宛先への送信は、形A・Bに当たらない小さな送信でも残量から差し引く。pf の通し先ルールは宛先のポートまで含める（`:8443` の承認で同じIPの `:443` は開かない。pf の構文上 `proto { tcp udp }` を付ける。`pfctl -nf -` の構文検査をテストに含む）。遮断ルールは IP 単位のまま（ポートを変えての迂回を防ぐ。誤遮断側に倒す）。保留中の宛先は小さな送信でも保留のまま。許可リストに入った宛先は、追加前に発行された送信請求が後から承認されても許可期限で再び閉じない。**残る穴**：承認端末の画面を乗っ取られたホストが作ると、画面は
正直でも「請求の中身そのもの」を偽れる（宛先を偽サイトにして「github」と書く等）。§4 の表示方式で
「表示＝署名対象」までは保証するが、「宛先が善か悪か」は人間の判断に残る。

**（6）承認疲れ対策。**
- 束ね：`BUNDLE_WINDOW`（20秒）内の保留は**1通の請求**に束ねる（試作で検証：5宛先→請求1通）。
- 間隔：新しい請求は最短 `MIN_BATCH_INTERVAL`（60秒）に1通。その間の送信は**保留側**に倒れる（承認を急がせない）。
- 番号照合：照合コード（2桁）は**ホスト側にだけ**表示され、承認端末で**入力**した値が署名対象に入る。画面を
  見ずに「承認」を押しても通らない（`code_mismatch`）。コードは請求本体には入れない。

## 4. 承認の経路（比較して一つ選ぶ）

| 案 | 無料 | 同期しない鍵 | 運用負荷 | 評価 |
|---|---|---|---|---|
| A. 自作 iOS アプリ（Secure Enclave） | ✗ 配布に Apple Developer Program が要る（有料。無料の個人署名は**7日で失効・3台まで**＝Apple 開発者フォーラム、二次情報）。OSS 利用者に配れない | ◎ | 重い | **不採用** |
| B. iPhone の Safari で WebAuthn | ◎ 利用者の追加費用なし | 端末内蔵パスキーは**iCloud 同期される**（Safari 16〜）→ 限界を明記。**セキュリティキー（FIDO）を使えば端末固定** | 軽い | **採用（既定）** |
| C. 既存 Tailscale 私設網＋Dispatchers | 経路としては ◎ | — | 署名機構が別途必要 | **B の到達経路として併用可（必須にしない）** |

**選定：B（Safari＋WebAuthn）。署名は ES256 固定。到達経路は利用者の任意の HTTPS（例：Tailscale Serve の `*.ts.net`）。予備鍵はセキュリティキーを推奨。**
理由：無料、OSS 利用者がそのまま使える、署名方式が Secure Enclave と同じ P-256 なので将来 A を足しても検証側が変わらない。

仕組み（設計。**WebAuthn アダプタは未実装**）：
1. Zee が請求（JSON）を作り、ホスト側に照合コードを表示、通知（既存 webhook/LINE 経路）で承認ページのURLを送る。
2. 承認ページは**請求JSONから署名対象を自分で計算して画面に表示**し、`challenge = payload_digest(請求＋入力コード)`
   で `navigator.credentials.get()` を呼ぶ。ページのJSは Zee 本体と別オリジンの静的配信（SRI固定）にして、
   乗っ取られたホストが画面と署名対象を食い違わせられないようにする（この分離をしない場合、ホストが乗っ取られると
   §3(5) の保証は崩れる。**言い切り**）。
3. Zee 側アダプタは WebAuthn の `authenticatorData‖SHA-256(clientDataJSON)` に対する署名を検証し、
   `challenge`・`origin`・`rpIdHash`・UP/UV フラグを照合してから、既存の `Verifier` 契約に流す。
- WebAuthn は HTTPS（または localhost）でのみ動く（二次情報）。LAN IP の素の HTTP は不可。

**有料提案の規程（案A を不採用とした根拠。Zee は無料配布で直接の収益は無い前提）**
1. 現在の頻度・量：情報なし（機能が未稼働で利用者0。計測していない）
2. 現在の1件あたりコスト：情報なし
3. 改善：推定のみ（確認済みの数字なし）
4. 金額換算：不能
5. 回収：回収対象の収益が無く、成立しない → **提案しない**。無料代替（案B）で同じ検証契約が満たせる。
   費用の上限：利用者のセキュリティキー購入（任意・数千円見込み・**未確認**）以外に Zee 側の支出は無い。

## 5. 保留中の通信の扱い

- **保持するのではなく、該当宛先への新規接続を切る**（`Enforcer.hold` → pf ブロック＋`pfctl -k` で既存の接続状態を破棄）。
  パケットを溜めて承認後に流す方式は、特権の透過プロキシか Network Extension が要り、標準ライブラリ・低権限の
  方針と衝突するため採らない（§10）。
- 遮断（`Enforcer.hold`）が失敗した宛先は保留済みとして記録せず「遮断待ち」として持ち、次の観測（送信量を問わない。期限切れは次の `tick`）で再試行する。
- 解除（`Enforcer.release`）が失敗した宛先は直前の状態（遮断は遮断、許可は許可）のまま残す。`disable` は設定を保存したうえで `release_pending` を返し、OFF の間は `tick` が解除を再試行する（OFF 中に再び閉じることはない）。同じ `allow_add` の再承認でも解除を再試行する。
- 送信側アプリは接続エラー／タイムアウトになる。承認後は同じ操作の**再試行**で通る（自動再送はしない）。
- 応答期限（`RESPONSE_TTL`、既定5分）を過ぎた請求は `timeout` として証跡に残り、**宛先は保留のまま**。
- 承認された宛先は `until`（既定15分）で再び閉じる。量の上限は**サンプリング粒度**で効く（最大で1サンプル分超過しうる）。
- 状態ファイルが壊れていた場合は、**ON・権限なし**として扱い、「承認が要る形」の送信はどれも通さない（フェイルクローズ。
  試作で検証）。復旧はホストコンソールからの手動。

## 6. 衝突の解き方（権限・依存）

Zee の方針は「標準ライブラリのみ・低権限・既定は観察のみ」。次を選んだ。
- **署名検証**：標準ライブラリに ECDSA は無い。**`openssl` CLI を呼ぶ**（`OpensslVerifier`。Zee が pfctl/nft/netsh を
  呼ぶのと同じ流儀）。P-256 の自前実装はしない。失うもの：openssl が無い環境（既定の Windows など）では検証できず
  **全拒否**になる。代替：`mcp` と同じ任意の追加依存 `[approval]`（`cryptography`）。**決定（2026-10-11）：当面は追加しない（openssl CLI のまま）。Windows 対応が要る段で再判断。**
- **強制**：プロセス単位の遮断には macOS の Network Extension（NEFilterDataProvider 等）が要るが、署名・配布に
  Apple Developer Program が要る見込み（**未検証**）で、OSS配布と方針に反する。→ **宛先単位の pf ブロックに倒した**。
  失うもの：同じ宛先に正規・不正のプロセスが混在する場合、プロセスを区別できない（承認画面にプロセス名は出す）。
- **試作は pf のルールを「文字列として出力するだけ」**。開発機のネットワーク・FW設定は変更していない。

## 7. 誤検知時の業務影響と復旧

- 影響：該当宛先への通信が最大で応答期限（5分）止まる。承認端末が手元にあれば1タップ＋コード入力で通る。
- 誤検知を減らす：①許可リストに入った宛先は絶対に止めない ②学習期間（§1）③`protect` を絞る（鍵ファイルのみ）。
- **承認端末が使えない時**：①予備鍵で承認（導入時に必須）②全部失ったら §3(2) の72時間リカバリー。
  ③緊急時の手動：既存の `zee restore`（自動遮断の復旧）と同じく、ホストコンソールから pf のアンカーを外せる
  （手順は `docs/maintenance/` に別途。**試作では未整備**）。
- 署名付き `disable` で OFF にすると、保留中の宛先は解放され（`Enforcer.release`）、以後は検知・通知だけが続く。
- 持ち出し承認を止めるには署名付き `disable` が要る。**承認端末が無く急いで止めたい場合の手段は、72時間待機の
  リカバリーしか無い**。これは意図した不便さ（**決定（2026-10-11）：停止手段は72時間待機のみ。緊急用の手動手段は作らない**）。

## 8. 既存機能との関係

- **構造的な分離**：検知・通知（`observe` の `egress_shape` 記録と通知）は ON/OFF スイッチを**読む前**に実行される。
  OFF でも、状態ファイルが壊れていても、証跡の書き込みが失敗しても、検知・通知・保留は止まらない（通知を先に出し、証跡・通知の失敗は握りつぶしてログに残す。試作で検証）。承認は応答段階にだけ繋がる。
- **自動遮断 ON/OFF（2026-10-08）**：許可状態モジュール `responder/permission.py` は
  main に入っているが**未配線**（ON/OFF の CLI・自動遮断の判定への接続は未実装）。本機能はその
  `HostLock`/`private_directory`/`private_temp` を import して使う。有効化状態の別経路を作らないため、**統合時は `auto_containment.json` と
  同じ許可状態ファイルへ `egress_approval` 項目として寄せる**（試作は `egress_approval.json` に分離。未統合）。
  持ち出し承認は自動遮断より狭い許可（OFF既定）で、**自動遮断の許可とは連動させない**。
- **証跡**：`egress.jsonl` に `egress_shape/hold/request/approved/denied/timeout/config_applied/recovery_*` を
  既存の hash chain（`EventLog._append`）で追記。署名値・公開鍵は記録しない。`verify_chain` で検証できる（試作で確認）。
  `zee export` への取り込みは**未実装**（別ファイルなので現状は対象外）。
- **MCP**：読み取りと提案のみ。承認・設定変更の操作はMCPに繋がない（`expose_actions` に載せない）。

| OS | 宛先・量の観察（権限不要） | 強制 | 状態 |
|---|---|---|---|
| macOS | `lsof`＋`nettop` のサンプリング（確認済み） | pf（root）。プロセス単位は Network Extension（未検証・不採用） | **試作の対象。実機でのpf適用は未実施** |

## 10. 止められるもの・止められないもの（言い切り）

**止められる**
- 許可リスト外の宛先への送信のうち、検知（サンプリング）より後の分（宛先単位）。
- 登録済み端末の署名が無い設定変更（許可リストの追加、保護対象の変更、承認の停止、端末の追加・削除）。
- 同じ署名の再使用、期限切れ、画面の内容と違う宛先・量での送信。

**止められない**
- **最初のサンプリング間隔に出た分**。巻き戻せない（時間稼ぎであって防止ではない）。
- **root を取られた後**：pf のルールも状態ファイルも書き換えられる。
- **Zee 自体を止められた後**：プロセスを kill される、状態を壊される（壊された場合は ON・権限なしになるが、
  プロセスが居なければ強制は働かない）。
- **オフラインで持ち出された後**：USB・物理コピー・撮影など、ネットワークを通らない持ち出し。
- **同一ユーザー権限の攻撃者による状態ファイルの直接書き換え**（0600 は同一ユーザーを防がない。`permission.py` の
  冒頭にも同じ注記あり）。改ざん「検知」は証跡の hash chain でできるが、「防止」は特権デーモン（root 所有の
  状態＋pf）に分離しない限りできない。これが PC の形の根本的な限界で、サーバーの形（専用ユーザー）は強い。
- **状態ファイルの削除**：壊れている場合は「ON・権限なし」だが、**無い場合は「未設定＝OFF」**として扱う（初回導入と区別できないため）。同一ユーザーの攻撃者は壊すより消す方が静かに OFF にできる。「一度 ON にした印」を別の場所に残す緩和は未実装（同じ権限で消せるため効果は限定的）。
- **承認端末の盗難＋端末ロック解除**、承認端末を持つ人間への偽装（社会工学）。
- 保護対象を**読まずに**手に入れる経路（バックアップ・同期サービス経由）。
