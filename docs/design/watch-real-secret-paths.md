# 設計案：本物の鍵ファイルの所在を「観察のみ」で監視する（watch_paths）

状態：設計案（未実装・未公開）。ブランチ `design/key-watch`。公開・マージは代表判断。
作成：2026-10-02

> この文書は汎用の仕組みだけを書く。特定マシンの鍵の所在一覧はここに書かない
> （本リポジトリは公開リポジトリ。所在一覧は攻撃者にとっての地図になる。SECURITY.md の
> 「assets.toml・パスは原則公開しない」と同じ扱い）。

## 1. 目的

開発機（AI エージェントが常駐し、本番サービスの鍵が集まる機械）では、侵入者の最短経路は
囮ではなく**本物の鍵ファイル**（`.env.local`、CLI の認証ファイル等）である。
囮だけを見ていると、本物の鍵が書き換え・持ち出しされても Zee は何も言わない。

## 2. 既存方針との関係（変えないこと）

- 書き込み（変更・削除・改名）は封じ込めの対象、読み出しは人の判断を残して通知のみ。
- ただし**本物の鍵ファイルは正規の利用者も日常的に書き換える**（CLI のログイン更新、
  `vercel env pull`、トークン更新等）。囮と同じ「変更＝自動遮断」を当てると誤遮断が日常化する。
- よって本物の鍵ファイルは **変更も読み出しも通知のみ**。自動遮断（auto / staged）の対象にしない。
  遮断は通知を見た人が `zee cut` で行う（既存の read-class と同じ扱い）。

## 3. `decoy_paths` を流用しない理由（検証済み）

`src/zee/decoy/seeder.py` の `seed()` は「パスが存在しなければ囮の中身を書き込む」。
本物の鍵ファイルを `decoy_paths` に入れると次の事故が起きる。

1. CLI が認証ファイルを「一時ファイル→改名」で書き換えている最中に Zee が再起動すると、
   その瞬間パスが無いため、**本物の鍵の場所に囮の中身が書かれる**（鍵が壊れる）。
2. 本物の鍵ファイルへの変更が change-class として扱われ、`response_mode="auto"` の資産では
   **正規の更新で遮断が発火**する。
3. 囮のヒット数と本物の鍵のヒット数が混ざり、`status` のバースト検知が意味を失う。

## 4. 提案：新しい項目 `watch_paths`

```toml
[[assets]]
id = "dev-mac"
type = "workstation"
response_mode = "notify"          # 既存。囮側の挙動
decoy_paths = ["~/Documents/zee-decoys/service.env"]

# 新設：本物の鍵ファイル。Zee は作らない・書かない・遮断しない。観察して通知するだけ。
watch_paths = [
  "~/path/to/project/.env.local",
  "~/.config/some-cli/auth.json",
]
```

挙動の約束：

| 項目 | decoy_paths（既存） | watch_paths（新設） |
|---|---|---|
| Zee が作成・書き込み | する（無ければ作る） | **しない**（無ければ警告だけ） |
| canary URL の埋め込み | する（設定時） | **しない**（本物の中身に触れない） |
| 変更・削除・改名の検知 | change-class → response_mode に従う | **secret-touch-class → 常に通知のみ** |
| 自動遮断 | auto/staged で発火 | **発火しない**（設定で変更不可） |
| 通知の文面 | 「囮に触れた」 | 「本物の鍵ファイルが変更された。心当たりが無ければ鍵の失効と `zee cut`」 |
| 権限の点検（追加） | なし | 起動時に mode が 600 より広ければ警告（直さない。直すのは人） |

イベント記録：`events.jsonl` に `class="secret_touch"`・`path`・`op`（write/delete/rename/attrib）・
`mode`（権限）を書く。**ファイルの中身・ハッシュは記録しない**（ログが二次漏えい源にならないように）。
`status` では囮のイベントと別の行に集計し、バースト検知の母数に混ぜない。

## 5. macOS で見えるもの・見えないもの（正直な限界）

| 事象 | 見えるか | 手段 |
|---|---|---|
| 本物の鍵ファイルの書き換え・削除・改名 | 見える | kqueue / EVFILT_VNODE（既存バックエンド） |
| 本物の鍵ファイルを**読むだけ** | **見えない** | kqueue は読み取りを通知しない（Apple の kqueue 文書・`zee capability` の出力どおり） |
| 本物の鍵の隣に置いた囮を読み、中の URL を辿る | 見える（設定時） | 既存の canary（`ZEE_CANARY_BASE_URL`） |
| 本物の鍵ファイルを開いたプロセスの記録 | 見える（別途） | Endpoint Security（`eslogger`）。root と「フルディスクアクセス」が必要＝本設計の範囲外・別判断 |

したがって macOS では「本物の鍵を盗み読みされた」ことは直接は分からない。補う手段は
**本物の鍵と同じディレクトリに囮を置く**こと（攻撃者は `.env*` を一括で読むので囮も読む）。
囮の名前は本物に似せる（例：`.env.production.local` の隣に `.env.backup`）。囮は既存の
`decoy_paths` で置くので、新しい仕組みは要らない。

Linux（inotify）では `IN_ACCESS/IN_OPEN` で読み取りも見えるが、本物の鍵は正規プロセスが
頻繁に読むので、読み取りイベントは既定で記録のみ・通知しない（通知の洪水を避ける）。

## 6. 実装範囲の見積もり（実装は代表承認後）

- `config/schema.py`：`AssetProfile.watch_paths: tuple[str, ...]` を追加（既定は空＝既存設定は無変更で動く）
- `cli.py watch`：`watch_paths` は `seed_all` に渡さない。存在確認と権限点検だけ行い、watcher に別ハンドラで登録
- `responder`：`secret_touch` クラスは遮断経路に入れない（型で分ける：遮断関数は `secret_touch` を受け取れない形にする）
- `status`：別集計行
- テスト：①watch_paths のファイルが無くても作成されない ②watch_paths の変更で遮断が呼ばれない（auto 資産でも）
  ③イベントに中身・ハッシュが入らない ④権限 644 で警告が出る

## 7. やらないこと

- 本物の鍵ファイルの中身を読む・ハッシュを取る・バックアップする
- 権限を自動で直す（chmod）・鍵を自動で失効させる
- 本物の鍵ファイルへの変更で自動遮断する
