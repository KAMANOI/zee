# 収録用シナリオ手順書（縦型ショート動画・X・note スクリーンショット）

前提：`demo/README.md` の「使い方」で venv を作成済みであること。収録は macOS 上で、Docker/VM を使わず `sandbox-exec` 隔離で行う（理由は README 参照）。

## 収録の流れ（手順）

0. 画面収録を始める：macOS 標準の「スクリーンショット」ツール（`Cmd+Shift+5`）→「画面全体を収録」または「選択部分を収録」。静止画の切り出しは `Cmd+Shift+4` または `screencapture -i out.png`（対話式・矩形選択）でよい。
1. ターミナルを縦型（9:16）の収録画面に収まるウィンドウサイズ・フォントサイズに調整する（下記「画面レイアウト」参照）
2. `source .venv-demo/bin/activate && demo/run_demo.sh` を実行
3. `make_dummy_files.py` が偽の書類ファイルを作る様子が流れる（任意：ここで `ls` して「普通のファイルが並んでいるだけ」を見せる一言カットを入れてもよい）
4. `zee watch is running ... Enter を押すと模擬攻撃を実行します` で画面が止まる → **ここで画面収録を開始**
5. Enter を押す → `mock_attacker.py` がサンドボックス内のファイルを書き潰し・`.locked` にリネームしていく様子がターミナルに流れる（約5〜10秒、ファイル名が次々 `.locked` に変わるのが画になる）
6. 直後、macOS のデスクトップ通知バナー（`Zee tripwire (change): demo-victim-pc` → 続けて `Zee dry_run: would cut demo-victim-pc`）が画面右上に出る → **ここで一度静止画を切り出す（スクリーンショット候補①）**
7. ターミナルに戻ると `zee watch` のログに `[event] ... mode=contain cut=no would_cut=yes` が並んでいる → **静止画候補②**（操作の一覧）
8. 続けて `zee status` の表が出る（検知件数・burst 警告） → **静止画候補③**
9. 最後に `[run_demo] done.` とサンドボックスディレクトリのパスが出て終了

収録時間の目安：Enter を押してから終了まで約20〜30秒（ショート動画の尺にそのまま収まる）。

## 画面レイアウト（9:16・縦型）

- ターミナルアプリ（Terminal.app / iTerm2）のウィンドウを縦長にし、フォントサイズは **20pt 以上** を推奨（スマホ画面での可読性）。`defaults write` 等の恒久設定は不要、収録用プロファイルを1つ作って使い回せばよい
- 1行が長い `[event] decoy write+extend+rename → mode=contain cut=no would_cut=yes` のような行は、ウィンドウ幅が狭いと折り返される。折り返されても情報は欠けないが、見た目を整えたい場合はウィンドウ幅を広めにして文字サイズで縦横のバランスを取る
- macOS の通知バナーは画面右上に出る。縦型キャプチャの画角に右上が収まっているか、収録前に一度テスト通知（`demo/run_demo.sh` を1回ドライで流す）で確認する
- ターミナルの背景は黒〜濃紺・文字は白〜緑系の高コントラストが、スマホの小さい画面でも読みやすい

## 静止画として切り出す画面（note 用）

1. **検知通知（dry_run 判定）**：macOS 通知バナー（`Zee tripwire` → `Zee dry_run: would cut`。実際に遮断したわけではない点を字幕等でも明示する）
2. **検知→遮断判定（dry_run）の一覧**：`zee watch` ログの `[event] ... would_cut=yes` の並び（`cut=no` ＝実際には何も遮断していないことが読み取れる形で見せる）
3. **検知サマリ**：`zee status` の出力（検知件数・burst 警告・`cut state: clear` ＝実遮断なしの確認）
4. （証跡機能完成後に追加）改ざん検知付き証跡の出力画面：`zee export` の結果。**現時点では未実施**（README「証跡出力について」参照）

## 非技術層向けの一言表現（候補）

**指示書内の例示「勝手にファイルを書き換える動きを、その場で止めます」は使わない。** Zee は書き込み操作そのものを止める設計ではなく、改ざんを検知した後にネットワークを遮断して被害の広がりを止める設計のため、この表現は Zee の実際の動作と一致しない（過剰主張。purpose card「Zee.md」の『防御率○%・回避不能・封じ込め保証を謳わない』方針にも反する）。

事実と一致する代替案：

- **「勝手な書き換えに気づいたら、データが外に持ち出される前にネットを切ります」（案1・2026-10-04採用）**
- 「乗っ取りに気づくのが遅れても、盗まれる前に通信を止めます」
- 「ファイルが書き換えられた瞬間を見張っていて、被害が広がる前に手を打ちます」
- 「"時間を稼ぐ"ための仕組みです。本職の対応が間に合うまでの猶予を増やします」（README の設計思想にもっとも近い表現）

いずれも「書き込みを防ぐ」「完全に守る」とは言わない。**非技術層向けの一言表現は案1を採用（G1・2026-10-04）。**

## 代表判断が必要な点

- 収録の画角・尺：20〜30秒のシーケンスで足りるか、もっと長い尺にするか
- 本物のネットワーク遮断（`dry_run: false`）を見せる収録を別途やるか（README「実際の封じ込めを本当に実行する収録はしていない」参照。VM/コンテナ環境の新規用意が前提）
